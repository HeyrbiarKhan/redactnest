# 0014. Detector follow ups

**Date**: 2026-10-14
**Updated**: 2026-10-15, from `/develop` on slice 1: the rescue runs after the possible pass instead of before it, joins only units both passes leave free, and skips its window lookup where no free unit is in reach. Run before that pass, it gave the first group of a number that is only possible to the row before it (`0131 410 5214 020 2977 5777` lost `2977 5777`), and on UK numbers side by side it lost more digits than today (6.7% against 5.6%), which broke AC-1's own bar. A check through `detect` then found that the rescue, in either place, could take a date's leading digits (`212 918 8665 1119 21 June 2014` cut the date to `June 2014`), because phone outranks date; AC-15 makes a rescued stretch yield to a date, which brings that loss to 0. A cross check on another model settled how the rescue picks its units, sums its reach and builds a joined row. AC-1, AC-2, AC-14, AC-15 (new), INV-1, INV-7 (new), the INV-13 and INV-14 amendments, a new AC-27 amendment, the Decision's first bullet, the data model and value sourcing rows, tasks 1 to 3, the test scenarios, the Consequences and the Follow-up are reworded; the measurements are in `rationale.md`.
**Status**: Proposed

## Summary

Feature 12 and its four reviews left a family of misses in spec 0005: a neighbour's digit group, or a footnote marker glued to a value, hides the value or gives it the wrong row. This spec settles them in one pass. The phone detector learns to rescue a digit group it would otherwise strand beside a number (today `9346 212 555 0123` lists `9346 212 555` and leaves `0123` in the file), after it has chosen every number it chooses today, so a rescue only ever adds a stranded group to a row and never takes a digit another row would have had; a group that also begins a date stays with the date. The find step learns that a small glyph raised or lowered off its line (a superscript, a subscript, an ordinal's letters) is not part of the text a detector reads, so a footnote marker can never glue to a value of any kind, and a row can never hold one, which today refuses the whole run. The one digit text rules feature 12 added stay for text that was read by OCR (optical character recognition, where a marker comes back as a plain digit), and gain the three cases the fourth review measured. Everything was measured on real MuPDF, on a page printed by Chromium, and on every string the detector tests and fixtures hold (1,258 of them) before it was chosen; the figures are in `rationale.md`.

## Requirements

**User stories**:
- As a visitor reviewing a document, I want a phone number that has digit groups beside it listed whole, so that no digit of it is left in the file next to a row that looks complete.
- As a visitor, I want a value followed by a footnote marker listed and removable whatever its kind and however the marker is drawn, so that a reference mark never hides an email address or a phone number, and ticking the row never fails the run.
- As the maintainer, I want the premise that MuPDF reads a raised marker as glued held by a test on a real raised glyph, so that an engine upgrade cannot quietly bring the miss back.

**Acceptance criteria**:

- **AC-1**: The phone detector runs its two choosing passes exactly as today (spec 0005, *Detectors* step 6: at each unit outside a chosen row the longest valid window starting there, then, over the units still free, the longest possible window holding only free units), and only then rescues stranded units, in one pass. A free unit is one neither pass took. The valid pass visits every unit outside a row it chose, so no free unit starts a valid window, and every valid window that covers a free unit starts inside a row the valid pass chose. Rows are numbered from 1 in the order chosen, the valid pass's first, so its rows are 1 to `validRows` (the count when it ends), and a join never renumbers a unit's row. The rescue asks at each unit whose row is one of those (its first unit included, whose windows the cache already holds, and any unit already joined to it), for the longest valid window starting there, through the window cache, but only where a free unit is in reach: for some free unit after it, the sum of `Unit.written` from the asked unit through that free unit, both included, is at most `MAX_WINDOW_DIGITS`, the same cap `windowsFrom` applies. The reach test ignores the date unit and slash stops `windowsFrom` also applies, on purpose: it can only ask more often than needed, never less, so skipping a lookup where no free unit is in reach changes no result. Units inside a possible row are never asked; they were free after the valid pass, so they start no valid window. Each stretch of free units the window covers joins the nearest row to its left: walking the window from the asked unit, the target row starts as the asked unit's row and becomes the row of each owned unit the walk passes, and each free unit joins the current target. That row may be one the possible pass chose. The order units are asked in changes no result, and a second rescue pass would join nothing, since the windows a unit starts never depend on which units are owned (argued in the code comment; no test seam reaches it). A row never takes another row's units, so every row the two passes chose keeps its start and every unit it held. A joined row's `start` stays its first unit's `start` (a `+` included), and its `end` becomes the last joined unit's end. Through `detect`, a joined row's rescued stretch then yields to a date (AC-15). So `9346 212 555 0123` lists one row `9346 212 555 0123`; `0131 410 5214 020 2977 5777` still lists `0131 410 5214` and `020 2977 5777`, because the possible pass takes `020` before any rescue runs; `212 526 5087 020 2208 1633 24` lists `212 526 5087 020` and `2208 1633 24`, where today `020` has no row; `6293 6608 0005 7382 276 020 7946 0958` lists the card and `020 7946 0958`; `212 555 0123 9346 415 234 5678` lists `212 555 0123` and `9346 415 234 5678`; `Box 2000 212 555 0123` still lists `212 555 0123` alone; `Ste 1 212 555 0123` still lists `1 212 555 0123`; `020 7946 0958 020 7946 0321`, `212 555 0123 212 555 0124` and every other side by side case in spec 0005's AC-27 still list each number alone. ## Decision

**Chosen option**: rescue stranded units in the phone chooser (not a merge of every overlapping window), an off line boundary in the find step by geometry and by code point with each short glued stretch read as a synthetic space and the target quads parted round it, and the text tolerances kept and extended by the three measured cases (reasoning and the other options in `rationale.md`).

- **The rescue, not the merge.** Merging every overlapping valid window, the card's rule, fixes the leak but glues 60% of random US numbers side by side into one unticked row, because a window across two numbers' middles is valid by chance. Rescuing only a unit that would otherwise be stranded keeps every pair apart (0% shared rows) and loses no digit anywhere today keeps one. Its cost is a tick: a UK number followed by a stray four digit group lists unticked, the group inside its row, about 12% of the time (92% ticked today, 80% after), and an unticked joined row removes none of its digits until the visitor ticks it. The runner up, a rescue only by a window at least as long as the row's own number, keeps 88% of those ticks but leaves 12% of US numbers leaking with three groups before (45% today, 6% with the chosen rule); the owner's rule, extra unticked rows are fine and missed values are not, decides it. The rescue runs last, after both of today's passes, so it only ever gives a row to a unit today's chooser leaves with no row, and no digit today's chooser keeps can be lost to it; run before the possible pass, as first drafted, it took `020` from `020 2977 5777` and left `2977 5777` in the file, and lost more digits than today on UK numbers side by side. Its lookup is skipped where no free unit is in reach, which changes no result and keeps numbers side by side at today's cost. And because phone outranks date, a rescued stretch yields to a date in `detect` (AC-15): the phone detector cannot see where the date detector reads a date, and a guard inside it (no join before a letter or a slash) would also stop the rescue of a number followed by a word, the commonest case in prose.
- **Geometry and code point, read as a join.** MuPDF keeps a raised glyph on its line, glued up to a 1 pt gap, and reports its rise and size exactly, so a glyph both smaller than its line and shifted off its baseline is a marker with no grammar to maintain. Size alone would drop small print on the same baseline (8 pt text inside 12 pt), and shift alone would wobble on OCR layers; both together flagged none of 78,856 real glyphs and none of a Chromium printed table with a 9 pt cell aligned middle. The size cap is 0.9 because Chromium's default superscript prints at 0.83, and the shift floor 0.15 because that cell sits at 0.06 while every superscript measured sits at 0.23 or more. A full size `¹` glyph has no geometry and only its code point, so the code point set is the second trigger. A short glued run reads as one synthetic space, none beside whitespace, because that is the one reading under which `27ᵗʰ September 2026` reads `27 September 2026` and `1980¹on` reads `1980 on`; dropping it with no space glues the next word, and keeping it as text breaks ordinals. The gluing rule and the cap keep a spaced value or an isolated word drawn small and shifted in the text. The target quads are parted round an off line stretch inside a span, because a line quad spanning the kept characters would still contain the raised letters of `27ᵗʰ` and target validation would then block the row as unsound.
- **Tolerances kept.** A boundary cannot see a marker that OCR returned as a plain digit on the baseline, and the fixtures draw exactly that. The three new tolerances take the fourth review's measured shapes; the bare Social Security one costs what the separated one already does.
- **Masking deferred.** Running lower kinds with a higher kind's positions read as spaces would tick the rescued `020 7946 0958` after a card and settle the card then date case; it changes how `detect` runs every kind and needs its own measurement, so it stays recorded under Follow-up.

**Implementation skills**: none; this is detector and engine code under the project's own rules.

## Feature design

**Data model sketch** (in memory only, nothing stored or sent):
- `Character` (spec 0005) is unchanged: `quad`, `origin` and `direction` already carry what AC-4 reads. `walkCharacters` still discards the size MuPDF reports, because the quad height is the same signal and is what the self check reads (spec 0004, `LINE_HEIGHT_MIN`).
- `pageText` in `src/engine/find.ts` buffers each line's characters before it writes them (lines are contiguous in extraction order), computes the dominant height and baseline, marks each glyph off line by AC-4 or AC-5, finds the runs, and writes each run that leaves as one synthetic space with `source` of -1, not listed in `joins`; a run that stays is written as ordinary characters. `PageText` and `BlockText` keep their shape, and each `Character` the page keeps is mapped as today. The find step keeps, per read, which characters are off line (a `Uint8Array` over `characters`), which `lineQuads` reads to part a span's quads (AC-7).
- `Window` in `src/detect/phone.ts` gains one optional field, `own`: the row's own window, set only on a joined row. The chooser keeps, across both passes and the rescue, an `owner` array (a `Uint32Array` over the run's units: the row each unit belongs to, counted from 1 in the order chosen, so 0 is a free unit) and a `rows` list of `{ window, last }` in that order, with `validRows` its length when the valid pass ends. A join sets `owner[index]` to the target row and that row's `last` to `index + 1`. At the end, a row nothing joined is returned as its own `Window` object, untouched; a joined row is returned as `{ ...window, end: run[last - 1].end, last, valid: false, own: window }`, so `start` and `reading` are kept; and the list is sorted by `start`. The possible pass's `freeUntil` reads `owner`, so it is built after the valid pass as today. *Detectors* step 7 reads an extension after each returned window's `end`, a joined row's included; a marker can only follow a run's last unit, so it never lands inside a joined row. No measurement switch (the prototype's `SKIP`) ships.
- `Span` in `src/detect/types.ts` gains one optional field, `rescued: { from, tickedByDefault }`, which `detectPhone` sets on a joined row from `own` (`from` is `own.end`, the tick is `ticks(own, points)`) and `detect` reads and strips (AC-15). No other detector sets it.
- `Unit.date` is set by AC-3's first rule as well as `isNumericDate`; the second rule acts in `unitAt`, where a hyphen glues the next group.
- Engine constants, beside `LINE_HEIGHT_MIN` in `src/engine`: `OFF_LINE_SIZE_MAX = 0.9`, `OFF_LINE_SHIFT_MIN = 0.15`, `OFF_LINE_STRETCH_MAX = 4`, `OFF_LINE_MIN_LINE_GLYPHS = 3`, `SUPERSCRIPT_CODE_POINTS` (a frozen `Set` built from the ranges AC-5 names). Detector constants in `src/detect`: none new; the tolerances are rules in `date.ts`, `us-ssn.ts` and `uk-nino.ts`.

**Key invariants**:
- **INV-1**: The rescue only adds. It runs after both choosing passes and joins only units both left free, so every row today's chooser lists is still listed with the same start and every unit it held, and no digit today's chooser puts in a row loses it. No digit a valid phone window covers is left without a row because another window was chosen: a unit a valid window covers either lies in a row or joins one (AC-1), since every shorter valid window from a start covers a part of the longest one. A rescue never takes a unit another row holds, so INV-13's "no unit belongs to two matches" still holds.
- **INV-2**: A joined row is never ticked (AC-2), so the rescue never removes a neighbour's digits by default.
- **INV-7**: The rescue never takes a position another kind's row holds today. Through `detect`, every position any of today's rows holds is still held by a row of the same kind: the rescue adds only units today's chooser leaves free, and a rescued stretch yields to every kind below `phone` (AC-15), so every lower kind's span resolves exactly as today.
- **INV-3**: A glyph off its line, by geometry or by code point, is never part of a span, a target's text or a target quad (AC-4, AC-5, AC-7), so no detector meets a real raised marker, the self check never meets one inside a ticked row, and removal never reaches one.
- **INV-4**: The boundary only removes positions from the page text; it never adds a character and never widens the text a span can cover. A run longer than `OFF_LINE_STRETCH_MAX` solid glyphs, or one not glued to a kept glyph, stays, so a spaced value or an isolated word drawn small and shifted is never dropped from detection.
- **INV-5**: A text tolerance drops nothing: it can only list a value that a glued digit hid, with the digit outside its row (spec 0005, INV-17).
- **INV-6**: Every rule here is measured before it lands, and the figures live in `rationale.md`; a rule whose cost on random codes is not recorded is not built.

**Security model**: unchanged. An anonymous visitor, one tab, no server call, the same for every tier. The boundary reads geometry inside the worker only, and nothing new crosses the boundary. The constants are rules about pages, not caps on the visitor, so they live in `src/engine` and `src/detect` where no environment variable can switch a check off (spec 0004, spec 0005, spec 0006, INV-7).

## Consequences

**Positive**:
- A phone number beside a stray digit group is never cut to leave part of itself in the file: one random group before a US number left digits with no row 36% of the time, three groups 45%; after the rescue 1.6% and 5.8% on the first round's layouts (0.0% and 0.0% on the build's), and a UK number after a spaced card is listed whole. Because the rescue runs last, no string loses a digit today's chooser keeps in a row (0 of 40,000 random strings), and UK numbers side by side lose fewer digits than today (2.9% against 4.1% on the first round's layouts, 4.6% against 5.6% on the build's).
- Because a rescued stretch yields to a date, a date beside a number keeps every digit it has today: 0 of 60,000 strings putting numbers, stray groups and dates side by side lose a position of any of today's rows, and a number then a date costs fewer ticks than without the yield (0.40% against 0.94% of strings).
- A footnote marker drawn the way word processors, typesetters and browsers draw one can no longer hide an email address, a phone number, a date with a two digit year, a bare Social Security number or a National Insurance number, and no row ever holds or covers the marker, so ticking a marked value never refuses the run. On the Chromium printed page in `rationale.md`, six of the eleven marked values give no row today.
- The boundary is one rule in one place for every kind, present and future, with no grammar to extend; the per kind text tolerances stay only for text that has no geometry.
- A real raised marker through MuPDF is held by a committed fixture and a test, so an engine upgrade that reads raised glyphs differently fails a test instead of bringing the miss back in silence.
- The INV-14 unit rules close the last two layouts where a numeric date reached a phone row, and the ISO interval's second date lists under Dates.

**Negative / tradeoffs**:
- A UK number followed by a stray four digit group lists unticked with the group inside its row about 12% of the time on the first round's layouts (92% ticked today, 80% after; a `+44` number 93% and 86%), about 9 points on the build's (73.5% and 64.2%, where a quarter of the numbers are only possible and never ticked), and a US number 0.3% with two groups after (0.2% on the build's); the visitor ticks it. Measured on 3,000 random layouts per shape.
- A number followed by digits the date detector does not read as a date, such as the spaced `16 07 1995`, lists unticked with the first group inside its row, as a stray group does: 0.40% of strings where a number is followed by a date in some form. And `detect` gains one step and `Span` one optional field (AC-15), which only `src/detect` sees.
- A joined row can hold digits of a second number when today's chooser leaves those digits with no row: `212 526 5087 020 2208 1633 24` lists `212 526 5087 020` unticked, where today `212 526 5087` is ticked and `020` stays in the file. So the first number loses its tick and the row reads wider than it, but no digit is left without a row. Measured on 1.2% of random UK pairs and 37 of 40,000 random strings; never on US pairs.
- The rescue does not cure a miss today's possible pass makes. A stray group before a UK number that is only possible is taken with the number's first groups as one possible row, and the number's last group is left bare: `01865 514994 0472 0117 853 0001` lists `01865 514994` and `0472 0117 853` and leaves `0001`, today and after. The first draft, which rescued before the possible pass, cured 11 such strings in 3,000 by accident while losing 8 that today lists, which is the 0.1 point gap in `rationale.md`; recorded in Follow-up with a candidate fix.
- An unticked joined row removes none of its digits by default: for `9346 212 555 0123` today's row removes seven of the number's ten digits and leaves three, the new row removes none until ticked. Nothing is hidden, and the row shows every digit, but a visitor who ticks nothing keeps the whole number where today they kept part of it.
- A joined row's text can hold a neighbour's digits (`9346 212 555 0123`), as a card's row can, so the row reads wider than the number.
- A glyph smaller than its line but on its baseline (small print glued to a value) is on the line for detection and off it for the self check's height rule (`LINE_HEIGHT_MIN`, 0.67 of the target quad's height), so a ticked row holding one refuses the run, as today. The boundary does not change this; recorded.
- A whole value drawn small and shifted, glued to a kept glyph, of up to four solid glyphs would leave the text; a spaced or longer one, or one not glued, stays. No fixture or scan shows the glued shape; the cap and the gluing rule are guards, not measurements.
- The evidence is this project's own fixtures (mostly Helvetica at one size), thirteen simulated scans from one OCR pipeline, and one Chromium printed page. Word, LibreOffice and LaTeX output and other OCR producers were not measured; the shapes they draw were reproduced from their documented sizes and rises. A producer that sizes each word from its box and sits baselines at the box bottom could meet the rule; the fixture test and the scratch flag count are the guards.
- The two digit year tolerance lists an unticked date on 6.4% to 6.7% of random `NN/NN/NNN`, `NN-NN-NNN` and `NN.NN.NNN` codes; the bare Social Security one on 89% of random ten digit runs after an SSN word; the National Insurance one is measured in task 8. The two digit year date unit in the phone detector (AC-3) keeps such a unit out of every phone window; its effect on the corpus is measured in task 7.
- Context lines no longer show a marker that stood after a value, since it left the page text; a visitor sees the space or the words after it.
- A row whose quads are parted round a raised ordinal is drawn as two black boxes with the ordinal's letters left between them.
- The find step buffers one line at a time and reads each line's glyphs twice; on `detect-dense.pdf` this is within the open budget spec 0012's AC-24 holds, to be confirmed by the speed project.
- Masking lower kinds by a higher kind's positions stays undone: the rescued number after a card lists unticked, and `5500 0000 0000 0004 05/12/2026` still lists a phone piece and a date piece. Through `detect` on OCR text, `SSN 223-45-6789¹` still leaves the ticked phone piece spec 0005 pins.

**Neutral**:
- `Character`, `FoundMatch`, `ReviewMatch`, `DetectInput` and the protocol are unchanged; the detectors' tests still build glued text by NFKC, because that is what reaches them from OCR text.
- The 2 s phone budget stays until the CI figure says otherwise.
- `detect-markers.pdf` is a new committed fixture; the existing footnote lines keep drawing a plain glued digit on purpose.
- The CI workflow gains one read only step; `tests/unit/workflows.test.ts` still holds that only the tag deploy writes.
