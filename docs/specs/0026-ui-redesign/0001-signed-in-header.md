# 0026.1. Signed in header

Child of [0026. UI redesign](index.md). Status follows the umbrella.

## Summary

The header shows who is signed in on every page, `/tool` included: an avatar with the first letter of the visitor's email, a menu with their plan, and "Open the tool" in place of "Try it free" (nothing on `/tool`). Pages stay static, so the header learns this in the browser. It reads Clerk's `__client_uat` cookie (read only) and asks our own `/api/entitlement` once only when that cookie says the browser signed in, so a signed out visitor sends nothing new and `/tool` sends nothing new at all. The email comes from a claim added to Clerk's session token, read locally on the server, returned to the visitor's own browser, and kept out of the worker, telemetry and storage.

## Requirements

**User stories**:
- As a signed in visitor, I want to see that I am signed in and which plan I have on any page, so that I never wonder whether Pro applies.
- As a signed in visitor on `/tool`, I want my account menu without losing my document, so that checking my plan never costs me my work.
- As a signed out visitor, I want the header to cost me nothing, so that the site stays fast and sends nothing about me.

**Acceptance criteria**:

- **AC-19**: With billing off, the header has no account slot, reads no cookie and makes no request. With billing on, the account slot (`src/app/account-slot.tsx`, `"use client"`, the header's only client component) decides through `browserSignedIn(cookieString)`, a pure function in `src/lib/entitlement.ts`: true when any cookie named by `^__client_uat(_[A-Za-z0-9]+)?$` (Clerk's plain and suffixed names; the suffix is never derived in the browser) holds an integer above 0. Its unit tests cover the plain name, a suffixed name, 0, a missing cookie, a non number and a forged large value. True means "this browser signed in"; then, on every page but `/tool`, the slot calls the store's existing `askAtLoad()`, one same origin `GET /api/entitlement`. False means no request and the signed out shape. On `/tool` the slot asks nothing itself: it subscribes to the same store, which `tool-client` fills as today, so `/tool` makes exactly the requests it makes today (spec 0002, AC-3; spec 0013, AC-21), and the slot shows `pending` until that answer lands, whenever `tool-client` asks. The cookie is read, never written, and nothing goes to storage.
- **AC-20**: The store gains `readIdentity()` (and the slot subscribes through `subscribeEntitlement`), returning `{ state: "pending" | "confirmed" | "unconfirmed", email: string | null }`. `pending` until a request settles. `confirmed` only when a response from our own server, read by `readSnapshot`, says `account: "signed-in"` or `"unknown"` (a genuine token whose plan check failed). `unconfirmed` for `"sign-in-needed"`, `"none"`, a failed or timed out request, an unreadable answer, and the store's own `FREE_ENTITLEMENT` fallback, which also says `unknown` but came from no server and so never shows the avatar. `confirmed` shows the avatar, `pending` the waiting circle (AC-25), `unconfirmed` the signed out shape (Sign in and Try it free). `sameAnswer` also compares the email, so a changed email notifies listeners, and when `keepsPaid` holds a paid answer over a later `unknown`, the kept answer keeps its email. The tool's own fail closed rule is unchanged.
- **AC-21**: The email source. Clerk's session token gains the claim `email` set to `{{user.primary_email_address}}` (dashboard, *Sessions*, *Customize session token*, on the development and production instances). `readSession` in `src/billing/session.ts` reads it from the verified payload on both paths (a live token, and an expired one proven genuine, spec 0012 INV-11), narrowed from `unknown` to a string holding one `@` and at most 320 characters, else `null`, and returns it in the `user` verdict. `resolveEntitlement` adds `email: string | null` to its answer: the claim for a genuine token (accounts `signed-in` and `unknown`), else `null`. `GET /api/entitlement` returns it with `Cache-Control: private, no-store`, as today. On the page, a new `readAccountEmail(body)` beside `readSnapshot` narrows it into the entitlement store's identity field. `readSnapshot` and `EntitlementSnapshot` are unchanged, so the email never reaches the worker: a unit test builds a snapshot from an answer that holds an email and asserts the frozen snapshot has exactly the four keys. The email is never logged, reported, put in a telemetry field, written to storage, or sent anywhere else: a unit test of the route captures every `reportServer` payload (an `unknown` answer with an email) and asserts it holds the event name alone. Two limits are accepted and stated in the privacy wording (AC-28): the claim is frozen when Clerk issues the token, and since no page outside the `(account)` group renews it, the address shown can be up to `SESSION_TRUST_MS` (7 days) old, the same window Pro is already trusted for (spec 0012, INV-11); and the claim carries no verification state, which is acceptable because the address is shown only to the browser holding that account's token.
- **AC-22**: The avatar is a 34 pixel `accent` circle with a 2 pixel `surface` ring and a `border` hairline, holding the email's first grapheme (`Intl.Segmenter`) uppercased with `en-GB`, in `on-accent` semibold. With no email it holds lucide's `User` icon. The letter and the icon are `aria-hidden`. The avatar is the menu's trigger, a `button` whose accessible name is `NAV_TEXT.yourAccount` ("Your account"). On `/tool` a "Pro" chip (`PRO_PLAN.name`, `accent-soft` fill, `accent-strong` text) sits before it when the tier is `paid`.
- **AC-23**: The menu (`DropdownMenu`, Radix, so arrow keys, typeahead, Escape and the focus return to the avatar are Radix's) is rendered with `modal={false}`, so it never sets `aria-hidden` on the rest of the page and `/tool`'s polite regions keep announcing while it is open. Its code (Radix included) is loaded with `import()` only once the identity is `confirmed`, so an anonymous visitor, on `/tool` or anywhere, downloads none of it. It holds, in order: a header block (the avatar, the email, and a plan line), then "Account" (`ACCOUNT_PATH`), then for `paid` "Billing" (`BILLING_PATH`) or otherwise "Upgrade to Pro" (`PRICING_PATH`, so the price is read before a checkout opens), then "Redact a PDF" (`TOOL_PATH`, a real page load; absent on `/tool`), then a separator and "Sign out" (`SIGN_OUT_PATH`, AC-26). Each item is a plain `a` (spec 0012, INV-13; never `next/link`, so nothing prefetches) with a lucide icon. On `/tool`, Account, Billing and Upgrade open a new tab with the `NEW_TAB` words `flow-text.ts` already uses, so the visitor's document stays open (spec 0012, AC-5 and AC-6 do the same); Sign out stays in the tab, and spec 0007's leave warning guards ticked work. The plan line is `ACCOUNT_MENU_PLAN` in `src/app/site-nav.tsx`, a record over `"paid" | "free" | "unknown"`: `paid` reads "{PRO_PLAN.name} · {paid} pages a document", `free` reads "{FREE_PLAN.name} · {free} pages a document" (caps from `config` through `countText`), and `unknown` reads "Plan unknown right now" (draft words, owner's read). Its key comes from the answer: `unknown` for account `unknown`, else the tier.
- **AC-24**: Signed in, the header's primary button reads "Open the tool" (`NAV_TEXT.openTool`, `TOOL_PATH`, `reload`) on every page but `/tool`, where there is none (it would point at itself, spec 0013 AC-7). Sign in is gone while signed in.
- **AC-25**: No flash and no shift. The slot reads the cookie and the identity through `useSyncExternalStore`, whose server snapshot is "hidden", so the server HTML and the first client render match (no hydration mismatch). The server HTML renders the slot at a fixed width (a `--spacing-account-slot` token in `@theme`, wide enough for Sign in and Try it free) with nothing visible in it, plus a `noscript` holding Sign in and Try it free, so a visitor without scripts keeps both. The slot stays hidden for the one render before hydration; then `browserSignedIn` false shows the signed out shape, and true shows a plain `muted` circle (`aria-hidden`, no accessible content) while the identity is `pending`, then the avatar or the signed out shape (AC-20). The header's layout shift is 0, measured by a Playwright test reading `layout-shift` entries on `/` signed in and signed out. The slot is the one client island the shared header may carry onto static pages, and only on a billing on build. Each check that holds a page to "no client component, no script" (spec 0011, INV-7 in `tests/unit/policy-pages.test.ts`; spec 0024, INV-5, `SEARCH_FILES`; and any other list found in that test when this is built) allows exactly `src/app/account-slot.tsx` by name and nothing else, and the pages themselves stay server components with no client component of their own. Files: `account-slot.tsx` sits in the `src/app` lint zone with that zone's existing walls restated (the tool client ban, `BILLING_IMPORTS` and `BILLING_SYNTAX`, the telemetry walls); it may import `@/lib/entitlement`, which `src/ui` may not, so it lives in `src/app` and passes `Avatar` and `DropdownMenu` what they show.
- **AC-26**: Sign out without Clerk's script on the page. `SIGN_OUT_PATH` (`/sign-out`, in `src/lib/routes.ts`) is a page in the `(account)` group, inside `src/proxy.ts`'s matcher (its test updated), `noindex` and absent from the sitemap. It loads Clerk as every account page does, shows the spinner before "Signing you out" in a polite region present from the first render (spec 0013, INV-13), and once Clerk has loaded calls `useClerk().signOut()` through the flow `src/app/(account)/sign-out.tsx` already holds, ending in `window.location.assign(HOME_PATH)` (spec 0012, INV-10). With nobody signed in it goes home at once. If Clerk fails to load, the page shows its failure line and a plain link home, as `ClerkWait` does for sign in. It is kept out of `src/app/sitemap.ts` and disallowed in `src/app/robots.ts`, with `robots: { index: false }` in its metadata. The menu's Sign out is a plain `a`, so the visit is an ordinary navigation and, on `/tool` with ticked work, spec 0007's leave warning fires first; a Playwright test ticks a row, picks Sign out and expects the warning. Signing out needs the page's script to run, so an embedded image or a prefetch of the address does nothing; a link to it from another site, once followed, signs the visitor out, a nuisance and not a leak, accepted (rationale).
- **AC-27**: Below `sm`, signed out: the lockup, Try it free, and the menu button whose menu holds the nav and Sign in. Signed in: the lockup, the avatar, and the menu button whose menu holds the nav and Open the tool (none on `/tool`). Both reflow at 320 pixels with 200% text and no sideways scroll.
- **AC-28**: The privacy policy changes before the merge, with a change entry dated on the day at the top of `src/lib/policy-changes.ts` (spec 0011, INV-3): the plan check's claim says `/api/entitlement` now also returns the visitor's own email address to their own browser, only to show it in the header, and never stores, logs or sends it on; claim C6's description of Clerk's sign in cookie says its token also carries the email address; and the page says the header reads Clerk's sign in time cookie in the browser to decide whether to ask. It states AC-21's two limits: the address shown can be up to 7 days old, and Clerk's token, which now holds the address, travels in a cookie with every request to our own origin, as it always has. Every line of the privacy policy and of `/security` that says the static pages run no script, or no script of their own, is read again and reworded for the account slot (on billing on builds) where it no longer holds. Any claim the change weakens is reworded, never left wider than the code.
- **AC-29**: Setup and a walk. The `email` claim is added on Clerk's development instance before the build's sandbox walk and on production before the deploy (spec 0012's Go live list gains the step). The walk, recorded in this spec's verify notes, checks on the dev server: `__client_uat` is readable from `document.cookie` (not `HttpOnly`) on our own origin; a signed in visit to `/` makes exactly one request to `/api/entitlement` and shows the right letter and plan line; a signed out visit makes none; `/tool` makes no extra request and shows the avatar and, on Pro, the chip; Sign out from `/tool` with ticked work raises the leave warning, then lands home signed out. Production repeats the last three after the deploy.
- **AC-30**: `/tool`'s header has two contents. With no document (`idle`, and `failed` after an open), the nav holds Security and Pricing, and the right side holds Sign in or the Pro chip and avatar, never Try it free or Open the tool. With a document on the page (`opening`, `reviewing`, `redacting`, `complete`, `lost`), the nav's place holds a file icon, the file name (truncated with an ellipsis, the full name in the element's text for assistive technology) and "· {n} pages" through `countText`, then "Open another PDF" and "Start over" before the right side. Those two are today's file bar controls, moved with their test ids, accessible names and spec 0007 focus moves; area A keeps its identity without them. `ToolClient` renders the page header on `/tool` (it alone holds the state), importing `PageHeader` from `src/app/site-nav.tsx` (allowed: the rule is that only `tool/page.tsx` imports `tool-client`, not the reverse), and `src/app/tool/page.tsx` stops rendering it. With billing off the right side is empty in both contents. Below `sm` the file context takes a second row under the lockup. Every link out of `/tool` stays a real page load. The file name appears only as text in the header: never in `document.title`, a URL, an `aria-label` of a landmark, or anything the account slot or telemetry reads.

## Decision

**Chosen option**: a cookie gated, same origin plan check reused by the header, with the email from a Clerk session token claim, and sign out through an account page.

The header's account slot reads `__client_uat`, asks `/api/entitlement` only for a browser that signed in (and never a second time on `/tool`), shows the email's first letter from a token claim the server reads locally, and signs out by linking to a page in the `(account)` group.

Why, in short: one endpoint keeps the plan logic in one place (spec 0012's decision table) and the tool's request count unchanged; the cookie gate means anonymous visitors, almost all traffic, cost nothing; the claim avoids a second outbound call inside the tool's 4 second budget. Runners up: asking on every page view (simpler, but a function call for every anonymous visit), and looking the email up at Clerk (no dashboard change, but a second outbound call per check). Full options: [rationale.md](rationale.md), *Signed in header*.

## Feature design

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/api/entitlement` | GET | Clerk's cookies only (no body, no query) | `tier`, `pageCap`, `maxFileBytes`, `account`, `email` (new, `string \| null`) | Clerk session token, verified locally | none: every failure is a free answer with its `account` (spec 0012, INV-2) |
| `/sign-out` | GET (page) | Clerk's session | signs out, then a full load of `/` | Clerk, in the `(account)` group | Clerk fails to load: failure line and a home link |

**Value sourcing**:
| Action | Value displayed | Source |
|---|---|---|
| Decide whether to ask | signed in time | `__client_uat` or `__client_uat_<suffix>` cookie, read in the browser |
| Avatar letter, menu email | email | the session token's `email` claim, read by `readSession`, returned by `/api/entitlement`, narrowed by `readAccountEmail` |
| Plan line, Pro chip, Billing or Upgrade | tier and account | the same answer's `tier` and `account` |
| Plan line caps | free and paid caps | `config.freePageCap`, `config.maxPages`, through `countText` |
| Plan line names | Pro, Free | `PRO_PLAN.name`, `FREE_PLAN.name` |
| Menu and header words | every label | `NAV_TEXT` (gains `yourAccount`, `openTool`, `signIn`, `billing`, `upgrade`, `signOut`, `openAnother`, `startOver` where not already elsewhere) and `ACCOUNT_MENU_PLAN` |
| `/tool` file context | file name, page count | the session's open document in `tool-client` state (today's file bar values) |
| Sign out landing | home | `HOME_PATH` |

**Key invariants**:
- The email never enters `EntitlementSnapshot`, the worker, a log, a report, a telemetry field or storage.
- `/tool` makes no request it does not make today; a signed out visitor makes no new request on any page.
- No Clerk script loads outside the `(account)` group; every way out of it is a full page load.
- The header never shows signed in on an answer it could not confirm (AC-20); the store's own fallback is never `confirmed`.
- The file name is header text only, never a title, URL or landmark label (AC-30).

**Security model**: the email is the visitor's own, read from a token Clerk signed and the server verified, returned only to the browser holding that token, with no shared cache. Nothing the browser sends chooses whose email comes back. The cookie read on the page decides only whether to ask, never what is shown, so a forged `__client_uat` costs one request and shows the signed out shape.

**Configuration required**: no environment variable. Clerk dashboard: the session token claim `email` on both instances (AC-29).

**Critical test scenarios**:
- Signed out on `/`: no request to `/api/entitlement`, Sign in and Try it free shown, layout shift 0, verifies **AC-19**, **AC-25**.
- Signed in on `/` (stubbed answer with an email): one request, avatar letter, plan line, Open the tool, menu by keyboard, verifies **AC-19**, **AC-22**, **AC-23**, **AC-24**.
- On `/tool`: request count equals today's, chip on `paid`, no Redact a PDF item, new tab items, verifies **AC-19**, **AC-23**, **AC-30**.
- `sign-in-needed`, failure, timeout, unreadable answers and the store's fallback show the signed out shape, verifies **AC-20**.
- A forged `__client_uat` makes one request and shows the signed out shape, verifies **AC-19**, **AC-20**.
- The snapshot built from an answer with an email has exactly four keys, and the route test covers the claim on a live token, an expired genuine one, and a malformed one, verifies **AC-21**.
- Sign out page: polite region from first render, lands home, verifies **AC-26**.
- Billing off: no slot, no cookie read, no request, verifies **AC-19**.

## Build plan

1. `readSession` reads and narrows the `email` claim on both paths; `resolveEntitlement` and the route add `email`; unit tests with the local key pair, and the `reportServer` payload test, satisfies **AC-21**
2. `browserSignedIn`, `readAccountEmail`, `readIdentity` with its three states, `sameAnswer` and `keepsPaid` carrying the email in `src/lib/entitlement.ts`; the four key snapshot test and the fallback never `confirmed` test, satisfies **AC-19**, **AC-20**, **AC-21**
3. `src/app/account-slot.tsx` and its lint zone: `useSyncExternalStore`, held width token, `noscript`, avatar, Pro chip, the lazily loaded menu (`modal={false}`) with `ACCOUNT_MENU_PLAN`, the signed in button; every "no client component" check allows the named island, satisfies **AC-20**, **AC-22**, **AC-23**, **AC-24**, **AC-25**
4. Small screen header for both shapes, satisfies **AC-27**
5. `/sign-out` page, its route, the proxy matcher and its test, `sitemap.ts` and `robots.ts`, satisfies **AC-26**
6. `/tool`'s header: `ToolClient` renders it, the file context and moved controls, billing off, the file name rule, satisfies **AC-30**

8. Privacy policy wording and change entry, satisfies **AC-28**
9. Clerk dashboard claim on development, the sandbox walk, the Go live step, satisfies **AC-29**
