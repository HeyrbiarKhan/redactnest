## Summary

RedactNest starts counting what happens (page visits, documents opened and redacted, refusals, steps toward Pro) and reporting when its code fails, without ever touching a document. Every event is a closed set of kinds and rough ranges (for example `2-5` emails found), carries no id and no cookie, and goes from the page to our own `/api/telemetry` route, which passes it on server to server: usage counts to Umami's free plan, errors to Sentry's free plan with an email alert. Neither service loads a script on any page, `/tool` keeps its `connect-src 'self'`, and the privacy policy changes in the same change. It costs $0 a month in services plus a few cents of Vercel function time, and nothing it does can bill the Vercel budget that pauses the site. Each failure report goes at most once an hour for each kind and place, and reports from pages share a small daily budget, so nothing a page or a script sends can use up Sentry's free quota ahead of a server failure.

## Requirements

**User stories**:
- As the owner, I want a count of each step from a visit to a paid plan, so that I can see where people stop, without ever holding anything about a document.
- As the owner, I want an email when something fails silently (the plan check falling back, the engine failing to load, a paid checkout that never turns into Pro), so that a paying visitor is never capped for days without my knowing.
- As a visitor, I want the site to send only counts that cannot be tied to me, and no counts at all when my browser asks for that, so that the privacy policy holds as written.

**Acceptance criteria**:
- **AC-1**: `TelemetryEvent` in `src/telemetry/events.ts` is a union of exactly the twelve events in *Data model sketch*. Every field is a closed kind from `src/worker/protocol.ts`, a closed list in `src/telemetry/events.ts`, or a `Bucket`, and no field holds a raw number. The gate in `tests/unit/loggable.test.ts` checks `LoggablePayload | TelemetryEvent`, so `pnpm typecheck` fails if any event gains a free string. `src/worker/protocol.ts` is unchanged, because the worker zone may not import `@/telemetry` (AC-24).
- **AC-2**: `bucket(n)` returns `"0"` for 0, `"1"` for 1, `"2-5"`, `"6-20"`, `"21-50"`, and `"51+"` for anything above 50. A map by kind (`bucketsByKind`) leaves out every kind whose count is 0 or absent, so `"0"` appears only where a field is a single count.
- **AC-3**: `parseTelemetryEvent(value: unknown)` returns a `TelemetryEvent` only when the name is one of the twelve and every key and value is one that event allows. Anything else returns `null`: an unknown key, a value outside its list, a number, an object where a kind belongs, a repeated item in `stripped`. The reporter and the parser read the same lists, so they cannot disagree.
- **AC-4**: `report(event)` in `src/telemetry/client.ts` sends one event as JSON in a `POST` to `TELEMETRY_PATH` (`/api/telemetry`, in `src/lib/routes.ts`) with `keepalive: true`, `credentials: "omit"` and `cache: "no-store"`. It returns nothing, is never awaited, swallows every failure, never retries and keeps no queue, so nothing the visitor does waits on it or changes when it fails.
- **AC-5**: The reporter sends only when `config.telemetryReporting` is true: `NEXT_PUBLIC_VERCEL_ENV === "production" || NEXT_PUBLIC_TELEMETRY_E2E === "1"`, both read literally in `RAW` in `src/config/index.ts` (`NEXT_PUBLIC_VERCEL_ENV` is added there; only `VERCEL_ENV` is read today). That is a Vercel production build or the Playwright build. Previews, `next dev` and every other build send nothing.
- **AC-6**: In a browser where `navigator.globalPrivacyControl` is `true` or `navigator.doNotTrack` is `"1"`, no usage event is sent (the seven in *Usage events*); error reports still go. On the server, no usage event is sent for a request carrying `Sec-GPC: 1` or `DNT: 1`.
- **AC-7**: `POST /api/telemetry` reads no cookie and sets none. It answers `413` without reading the body when `Content-Length` is over 2048, and stops reading a body that runs past 2048 bytes without one, dropping it with a `204`. Every other request it answers `204` with no body and `Cache-Control: no-store`, forwarding the event only when (a) `Sec-Fetch-Site` is `same-origin`, or that header is absent and `Origin` equals `config.siteUrl`'s origin, and `Content-Type` names `application/json` (the media type before any `;`, trimmed, in any letter case, so `application/json; charset=utf-8` passes), both checked after the `413` size check and before the body is read, (b) `parseTelemetryEvent` accepts it and `isBrowserEvent` does too (`BROWSER_EVENTS`, *Data model sketch*), so a script can't post a server only event such as `server-crash` or `plan-check-failed`, (c) sinks are configured, and (d) for an error report, the collapse (AC-27) and the page budget (AC-29) admit it. Otherwise the event is dropped with the same `204`.
- **AC-8**: An accepted event is forwarded after the answer, inside `after()` (`onRequestError` has no answer to wait for, so it calls `forward` directly and awaits it, as Next.js's docs require): a usage event to Umami's send endpoint, an error event to Sentry's envelope endpoint, each with a 3 second timeout, every failure swallowed and never retried. The outbound request holds only what *Value sourcing* names for that sink and a fixed `User-Agent`. It never holds the visitor's IP address, `User-Agent`, cookie, referrer or any other header of the incoming request.
- **AC-9**: `UMAMI_WEBSITE_ID` and `SENTRY_DSN` are both set or both absent. Each of these fails the build, with every problem in one error as the launch gate does: a build with one value; a Vercel production build with neither; a Vercel build that is not production with either; a Vercel build with `NEXT_PUBLIC_TELEMETRY_E2E` set; a website id that is not a UUID; a DSN that is not `https://<key>@<host>/<project>` on a host ending `.sentry.io`. Off Vercel, sinks are never configured.
- **AC-10**: A reporter mounted once in the root layout sends `page-view` with the page's `PageKind` on every page load and on every client side pathname change. It reads the pathname only, never the query or the hash. A pathname no kind names is `not-found`; files such as `/licence.txt` send nothing.
- **AC-11**: The tool's events come from session transitions: an effect in `tool-client.tsx` compares the previous session with the next. When an open succeeds (the session leaves `opening` for `reviewing`), the tool sends `document-opened` once: `pages` from `summary.pageCount`, `found` and `blocked` from `detectionCounts`, `pagesWith` from `countPagesByFinding(summary.pages)`, and `tier` and `account` from the job's frozen entitlement.
- **AC-12**: When a run completes (the session leaves `redacting` for `complete`), the tool sends `redaction-completed` once, built from `resultCounts` (`removed`, `unticked`, `blockedByKind`, `blockedByReason`, `stripped`) with `tier` and `account`. A rerun sends again.
- **AC-13**: The tool sends `run-refused` when an open fails (`opening` to `failed`, the kind from the new `failure`), when a run is refused (`redacting` back to `reviewing` with a new `runFailure`, which is its kind), and when the session reaches `lost` (kind `engine-unavailable`). `step` is `redact` when the previous state was `redacting`, and `open` otherwise. A free tier `too-many-pages` or `too-large` sends `cap-reached` instead (`cap` is `pages` or `size`, with `account`), so one refusal is one event. A cancel sends nothing. Neither does the silent retry while the engine was still loading (spec 0002, AC-11a): its `worker-lost` and `retry` land in one render, so the session never shows `lost`.
- **AC-14**: `subscribe-started` is sent by the server when Subscribe's outcome is `checkout`, scheduled before the redirect. `subscription-confirmed` is sent when `WelcomePoll` first reaches `pro`, once per page load. Nothing we send counts a finished sign in or sign up: the funnel's sign in step is read from Clerk's dashboard, which counts each one on Clerk's side, the Get Pro path included (Go live step 8). There is no `sign-in-completed` event and no `SignInDone`, so the sign in and sign up pages render our panel and Clerk's card only (`tests/unit/billing-landing.test.ts`), and the only telemetry they post is AC-10's `page-view`.

In Next.js 16.3.5 the hook hears page renders, route handlers and server actions, never the proxy, so the proxy reports its own failures (AC-26). `routeKindFor` keeps mapping `routeType: "proxy"` to `proxy`, so a later Next.js that does call the hook for the proxy lands on the same kind. The hook and the proxy are built as separate bundles, each with its own memory for AC-27, so after such an upgrade one proxy throw would send two reports until the proxy's catch comes out (Follow-up).
- **AC-16**: `/api/entitlement` reports `plan-check-failed`, after its answer, whenever it answers `account: "unknown"`, through the collapse (AC-27), so a Polar outage sends one report an hour from each server instance, not one for each signed in `/tool` load.
- **AC-17**: The root layout reporter listens for `error` and `unhandledrejection` on `window`. An `error` event whose `filename` is on the page's own origin sends `browser-crash` with the page kind and `kind: "error"`; an `error` from another origin (a browser extension) sends nothing. Every `unhandledrejection` sends it with `kind: "rejection"`, whoever caused it, by design: a rejection carries no origin we can trust (its reason is often not an `Error`, and stacks differ by browser), so the page load cap (AC-28), the collapse (AC-27) and the page budget (AC-29) bound the noise instead. The message, filename, line and stack are read only for the origin test and never sent.

A silently retried loss sends nothing (AC-13).

Manage billing reports `action: "portal"` for `portal-failed`. No argument, email, id or message from a billing seam is read into a report.

The envelope's header is `{ event_id, sent_at, dsn }` and its one item header is `{ type: "event" }`; the `dsn` header is the authentication. It carries no `exception`, `stacktrace`, `breadcrumbs`, `user`, `request`, `contexts`, `extra` or `server_name`.
- **AC-21**: A `page-view` becomes an Umami page view for the page's path (*Value sourcing*). Every other usage event becomes an Umami event named as in the catalog, with its fields flattened (`found_email: "2-5"`) and the hostname from `config.siteUrl`. `stripped` becomes one `true` property per kind present (`stripped_annotations: true`), and a by kind map with nothing in it adds no property. It carries no referrer, language, screen or title. Its `User-Agent` is the fixed string Umami's docs give for server sends; if Umami's bot filter refuses that, one fixed generic browser string, the same on every event and never the visitor's. The worst case event (every kind present) fits Umami's property limit, read from Umami's docs at build. If the limit is lower, `redaction-completed` splits as *Data model sketch* says.

After the deploy, step 7's visit and test error each arrive. Step 8's read of what Clerk's dashboard shows is recorded in `rationale.md`, before or after the merge.
- **AC-26**: A throw, or a rejected promise, inside `proxy` in `src/proxy.ts` reports `PROXY_CRASH` (`server-crash` with `route: "proxy"` and `routeType: "proxy"`) through `reportCrash`, awaits it, then rethrows the same error, so Next.js answers exactly as it does today. `proxy` becomes `async`. The billing off return stays above the `try`, so with billing off there is nothing to report; the `try` holds `withoutPortalToken`, the 307 and `return await clerk(request, event)`, because a bare `return` would let a rejection slip past the catch. It reads nothing from the error or the request. A Next.js control flow throw (its redirect or not found errors) can't arise here: the proxy gives Clerk no callback and calls neither `redirect()` nor `notFound()`, so the catch has nothing to skip.
- **AC-27**: Every error report goes through one collapse in `src/telemetry/server.ts`, keyed on `reportKey(event)` from `src/telemetry/events.ts`: the event's name and the value of each of its fields, in `EVENT_FIELDS` order (`server-crash home render`, `plan-check-failed`). It admits a report only when no report with the same key went through the same memory in the last `REPORT_WINDOW_MS` (one hour); at exactly one hour it admits again. That memory is held per bundle, not shared by the whole server instance (INV-10): on one instance the hook and `/api/telemetry` keep separate memories, as the proxy keeps its own. `reportCrash(crash)` (the hook and the proxy, awaited, as AC-8 says for the hook) and `reportServer(event, headers)` (request code and `/api/telemetry`, scheduled in `after()`) both decide through it, each taking the memory as its last parameter, a seam that defaults to the module's `REPORT_MEMORY`, so `server-crash`, `plan-check-failed`, `billing-failed`, `browser-crash` and `engine-unavailable` all collapse alike; usage events never pass through it. The check and the record happen together, with no `await` between them, before any send is started, so a repeat that arrives while the first is still in flight is skipped too. A send that fails or times out still counts, so the next report with that key in the hour goes unsent: a lost report, never a second one. With no sinks nothing is recorded. A clock that throws drops the report and records nothing. `reportCrash` never rejects (its body is guarded as `onRequestError`'s is), so the proxy always rethrows its own error. In `reportServer` the decision sits inside its existing `try`, after the sinks and opt out checks: a report the collapse drops schedules nothing, and if `schedule` throws after the record (`after()` outside a request), the report is lost for the hour and nothing is taken back, the same rule as a failed send. It reads only the event and the clock. So a failed page sends one report however many times Next.js calls the hook for it, provided every call maps to the same `route` and `routeType` (verify measured that): the hook is called once for a failed page, and two or three times only when `not-found.tsx` throws as well. A route failing on every request sends one report an hour from each server instance.
- **AC-28**: In the browser, `report` sends each error report at most once per page load. The cap goes by category: it holds every error report (`ERROR_EVENTS`), whichever code sends it, not only those `isBrowserEvent` accepts. It keeps the `reportKey` of every error report it has sent in a module level `Set` in `src/telemetry/client.ts` (a deliberate cache, never browser storage, of at most the 24 shapes a page sends: `browser-crash` on 11 page kinds by 2 sources, `engine-unavailable` and `still-waiting`), and returns without a request when the key is already there. A full page load starts it empty; a client side navigation keeps it. A key goes in only when a request is made, so a report the gate (AC-5) stops leaves nothing behind. Usage events are never capped: each one counts.
- **AC-29**: `/api/telemetry` forwards at most `PAGE_REPORTS_PER_DAY` (20) page error reports a day from each server instance, `still-waiting` aside. A page error report is an error report `isBrowserEvent` accepts (`browser-crash`, `engine-unavailable`, and `billing-failed` only as `welcome` and `still-waiting`): every error report the route can forward and none that server code sends. That rests on a rule this spec keeps: server code never sends one of those three shapes (today it sends `server-crash`, `plan-check-failed` and `billing-failed` for `subscribe`, `portal` and `delete` only). So a server report never spends the budget, and a forged report can spend nothing else. Every page error report draws on the budget except `still-waiting` (`drawsOnPageBudget` in `src/telemetry/server.ts`): it is a paying customer who never got Pro, so it neither spends the budget nor waits on it, and the collapse alone holds it to one an hour (AC-27), as it holds a server report; a forged one costs at most that, about 720 a month from each server instance. The day is the UTC day of `seams.now()` (`Math.floor(time / 86_400_000)`), so the budget starts again at midnight UTC, and on every cold start and every deploy. The budget is asked only after the collapse admits a report (AC-27), and a report counts once both admit it, before any send starts, so a send that then fails still counts, as in AC-27. Once the day's 20 are gone, the other page error reports are dropped until the day turns, and a dropped report records nothing, neither in the budget nor in the collapse. Rejections can use up the day by themselves: `kind: "rejection"` is unfiltered by design (AC-17), so an extension's or another service's script rejecting on each of the 11 page kinds spends 11 in the first hour and all 20 within about two, and every page error report but `still-waiting` then waits for midnight UTC. A quiet day of `browser-crash` and `engine-unavailable` in Sentry is no proof that pages worked. Server reports have no budget: the collapse alone holds them.

## Decision

**Chosen option**: Option 2, our own route forwarding to Umami Cloud (usage) and Sentry (errors), both on free plans, both called by plain HTTP with no SDK.

Every page reports closed events to `/api/telemetry`. The route checks and forwards them server to server, so no outside script, cookie or origin reaches any page. Options and reasoning: [rationale.md](rationale.md).

Decisions made in the design (each with its runner up in [rationale.md](rationale.md), *Small choices*): no SDK for either service; forward inside `after()`; `204` for every read body; `cap-reached` instead of `run-refused`; `still-waiting` as a billing failure; no count of a finished sign in, because Clerk's dashboard holds that step (decided 2026-11-02, after the verify walk); the proxy catches and reports its own failures, and every `server-crash` reports at most once a minute for each route and type (both decided 2026-11-03, after the verify walk; the minute became an hour on 2026-11-04); every error report at most once an hour for each report, each error report at most once per page load in the browser, and a daily budget of 20 page reports for each server instance in place of a Sentry key limit the free plan doesn't offer, with rejections kept unfiltered, an unknown route type reported as `other`, and the route requiring JSON (all decided 2026-11-04, after the review); the console ban not lifted; an e2e build flag for the browser proof; a new capability folder `src/telemetry`; no bot filter.

## Feature design

**Data model sketch**: no persistence. The events are the model, and we store none of them; history lives in Umami (6 months) and Sentry (30 days).

`Bucket` = `"0" | "1" | "2-5" | "6-20" | "21-50" | "51+"`. `PageKind` = `home | tool | pricing | privacy | terms | sign-in | sign-up | account | billing | welcome | not-found` (any path under `/account` that the list doesn't name, such as Subscribe's failure page, is `account`). `Tier` = `free | paid`; `account` is `EntitlementAccount`.

*Usage events* (to Umami; not sent under GPC or DNT):

| Event | Sent by | Fields (all required unless marked) |
|---|---|---|
| `page-view` | browser, root layout reporter | `page: PageKind` |
| `document-opened` | `/tool` | `pages: Bucket`, `found: Partial<Record<DetectorKind, Bucket>>`, `blocked: Partial<Record<BlockedReason, Bucket>>`, `pagesWith: Partial<Record<PageFinding, Bucket>>`, `tier`, `account` |
| `redaction-completed` | `/tool` | `removed`, `unticked`, `blockedByKind: Partial<Record<DetectorKind, Bucket>>`, `blockedByReason: Partial<Record<BlockedReason, Bucket>>`, `stripped: readonly SanitizedKind[]` (no repeats), `tier`, `account` |
| `run-refused` | `/tool` | `kind: EngineErrorKind`, `step: "open" \| "redact"`, `tier`, `account` |
| `cap-reached` | `/tool` | `cap: "pages" \| "size"`, `account` |
| `subscribe-started` | server, Subscribe | none |
| `subscription-confirmed` | browser, `WelcomePoll` | none |

No event counts a finished sign in or sign up (AC-14). That step of the funnel is read from Clerk's dashboard, beside Umami's `page-view`s of `sign-in` and `sign-up`.

*Error reports* (to Sentry; never stopped by an opt out, and held by the collapse, the page load cap and the page budget, AC-27 to AC-29):

| Event | Sent by | Fields |
|---|---|---|
| `server-crash` | server, `onRequestError` and the proxy's own catch, both through `reportCrash` | `route: RouteKind`, `routeType: "render" \| "route" \| "action" \| "proxy" \| "other"` |
| `plan-check-failed` | server, `/api/entitlement` | none |
| `browser-crash` | browser, root layout reporter | `page: PageKind`, `kind: "error" \| "rejection"` |
| `engine-unavailable` | `/tool` | none |
| `billing-failed` | server (Subscribe, Manage billing, Delete account); browser (`WelcomePoll`) | `action: "subscribe" \| "portal" \| "delete" \| "welcome"`, `outcome: "plan-unknown" \| "customer-conflict" \| "other-product" \| "checkout-failed" \| "portal-failed" \| "billing-failed" \| "sign-in-kept" \| "still-waiting"` |

`RouteKind` = `home | tool | pricing | privacy | terms | not-found | entitlement | telemetry | account | subscribe | billing | welcome | sign-in | sign-up | proxy | other`. `ROUTE_KINDS` maps each route file's `routePath`, as Next.js 16 reports it, to a kind. The build reads the real strings by throwing once in each route locally and records them in the map's comment; `routeType: "proxy"` maps to `proxy` whatever the path. In Next.js 16.3.5 only the proxy's own catch sends `route: "proxy"` (AC-26); the hook never hears the proxy.

`BROWSER_EVENTS`, the only events `/api/telemetry` forwards (AC-7): `page-view`, `document-opened`, `redaction-completed`, `run-refused`, `cap-reached`, `subscription-confirmed`, `browser-crash`, `engine-unavailable`, and `billing-failed` only with `action: "welcome"` and `outcome: "still-waiting"`. Everything else (`subscribe-started`, `server-crash`, `plan-check-failed` and the server's `billing-failed`) is sent by server code alone.

Relationships: none, on purpose. No id, no session, no timestamp from the browser, no join key: the funnel is read from totals. Sentry's `event_id` is made fresh on the server for each report and links nothing.

Split, only if Umami's property limit is below `redaction-completed`'s worst case (38 properties: 7 removed, 7 unticked and 7 blocked detector kinds, 4 blocked reasons, 11 stripped kinds, plus `tier` and `account`): it becomes `redaction-completed` (`removed`, `stripped`, `tier`, `account`) and `redaction-left` (`unticked`, `blockedByKind`, `blockedByReason`), both sent at the same moment.

**State transitions**: none of its own. Events fire on transitions that already exist: the session leaving `opening` or `redacting`, or reaching `lost` (AC-11 to AC-13); `WelcomePoll`'s phase reaching `pro` or `still-waiting`; Subscribe's, Manage billing's and Delete account's outcome kinds; `/api/entitlement`'s `unknown` answer; a server request erroring.

**Key invariants**:
- **INV-1**: Counts and kinds only. Every event is closed (AC-1, AC-3), and no raw count leaves the browser or the server, only buckets.
- **INV-2**: Nothing ties two events to each other or to a person. There's no id and no cookie (`credentials: "omit"`, and the route reads none), and no visitor detail is forwarded (AC-8).
- **INV-3**: Telemetry never changes what a visitor sees or waits for. It is never awaited, never throws into a caller and never retries (AC-4, AC-8). The one wait is on a server failure already under way: the hook and the proxy's catch await their send (at most 3 seconds, and only the first in an hour for each report, AC-27), as Next.js's own hook does, and the visitor then gets the same error page as without it.
- **INV-4**: Nothing from anyone else on any page, and no new origin anywhere. No Umami or Sentry script or SDK exists in the bundle; forwarding is server to server; their `OUTSIDE_SERVICES` entries name no origin; `/tool`'s policy is unchanged (spec 0001, spec 0011 INV-2).
- **INV-5**: No metered Vercel product. Web Analytics, Speed Insights, Observability Plus and drains stay off (spec 0011, INV-9, unchanged). The only Vercel cost is function time for `/api/telemetry`, held down by the firewall rule.
- **INV-6**: An opt out stops usage counts, never error reports (AC-6).
- **INV-7**: Our own code still writes no log (claim C8, spec 0011 AC-15).
- **INV-8**: Production only (AC-5, AC-9).
- **INV-9**: A quota can only drop events, never bill. Both services are on free plans with no card on file (*Go live*), so a flood costs data, never money.
- **INV-10**: No page sent or repeated report can crowd out a server report. A repeat of any error report waits an hour (AC-27), a page sends each error report once per load (AC-28), and page error reports but `still-waiting` share a daily budget that server reports never draw on (AC-29). So from each server instance, page reports take at most about 600 of Sentry's 5,000 a month and `still-waiting` at most 720 (one an hour), and one server failure that keeps happening takes at most 720 (one an hour): a new server failure's first report finds room unless several failures are left running for weeks. Every limit is keyed on the event's own closed fields, never on the error or the request, and held in memory on each server instance and in each bundle (the hook's, the proxy's and `/api/telemetry`'s each apart). Sentry's free plan can't rate limit a key, so nothing outside our code backs these limits up.

**Security model**: anonymous throughout. The browser sends events with no cookie; the route trusts nothing it receives and forwards only what the parser rebuilds from closed lists, so a forged event can skew the counts but can't carry text anywhere, and it can never be a server only event (`BROWSER_EVENTS`), so a script can't trigger the server alerts. Same origin requests only (AC-7) stop other sites using their visitors' browsers; a script calling the route directly is held to about 30 a minute per IP by the firewall rule, and whatever its addresses, it can spend only the page budget (AC-29), 20 page reports a day from each server instance, which no server report draws on, and one `still-waiting` an hour, which the collapse holds. The two values are server only, never `NEXT_PUBLIC_`: the website id and the DSN never reach a browser, so nobody can post to our Umami or Sentry projects directly from a page. Importers: `@/config/telemetry` is imported only by `src/telemetry/server.ts` and `src/app/layout.tsx` (for the build gate). `@/telemetry/server` is imported only by `src/app/api/telemetry/route.ts`, `src/app/api/entitlement/route.ts`, `src/instrumentation.ts`, `src/proxy.ts` (which shares the `(account)` group's lint zone, so lint already allows it) and the `(account)` group. `@/telemetry/client` and `@/telemetry/events` are imported by `src/app` and `src/lib`. Billing seams are never handed to telemetry: a page passes its outcome `kind`, never the outcome object. **Compliance scope**: UK GDPR and EU GDPR. The events hold no identifier and no IP, so they are meant to be anonymous. The policy still names both services, their location, safeguard and retention, and the legal basis (legitimate interests: keeping the service working and improving it). Global Privacy Control is honoured for usage counts (AC-6). **Audit**: none of our own, by design (spec 0001).

## Consequences

**Positive**:
- The funnel is visible end to end: visit, open, complete, cap, subscribe and confirmed in Umami, with sign ups and sign ins from Clerk's dashboard, which counts every one exactly. The silent failures spec 0012 worried about (the plan check, a paid checkout without Pro) now email you.
- Specs 0004 to 0007 get the refusal and finding counts their Follow-ups wait on.
- The privacy story stays structural: closed types and a parser, not a scrubber. There is nothing to scrub because there is nowhere to put anything (spec 0002).
- $0 a month in services, and no path from a flood of events to the budget that pauses the site.
- A broken Clerk setup on the sign in and account pages now emails you (AC-26), where before it showed only in Vercel's one day logs. A failed page is one report, even in the rare case where `not-found.tsx` throws too and Next.js calls the hook two or three times.
- No page, script or repeat can use up Sentry's month ahead of a server failure (INV-10): a repeat waits an hour, page reports share 20 a day from each server instance, and server reports never draw on that budget. It needs nothing beyond Sentry's free plan, and a looping page sends one report, not one per loop, so it no longer spends the visitor's 30 a minute firewall allowance that their counts share.

**Negative / tradeoffs**:
- No per visitor funnel: conversion is read from totals, so a visitor who opens three documents and one who opens one look the same.
- The sign in step lives in Clerk's dashboard, not Umami, so the funnel is read across two dashboards, as daily totals, and each may draw its day on a different clock. What Clerk shows is Clerk's to change (Go live step 8 records it).
- Debugging is slower: a report says only kind and where. The stack is in Vercel's runtime logs, which Next.js writes and Vercel keeps for one day.
- Two more outside services in the policy, and in feature 17's DPA, each with free terms that can change. A change to billing would break INV-9 and must come back here.
- History is short: Umami's free plan keeps 6 months, Sentry's 30 days.
- Counts are approximate: GPC and DNT browsers send none, bots that run scripts are counted, anyone can post forged but well formed browser events within the firewall limit, and visitors sharing one address (an office network) lose events past about 30 a minute.
- Umami's visitor, session and country panels mean nothing here: every event reaches Umami from Vercel's servers with one fixed `User-Agent`, so it sees one visitor in the function's region. Read Umami for event and page totals only.
- Every event costs a Vercel function call. That's a few cents a month at expected volumes, but it's no longer zero, and the per unit rates weren't confirmed.
- One more place a production build can fail (AC-9). It fails safe: the last deploy stays live.
- An issue's count in Sentry means hours with that failure on one server instance, not failures, and it rises with how many instances Vercel runs at once; a cold start begins with an empty memory. A second failure of the same kind in the same place inside the hour sends nothing, and so does one that follows a send that failed. It would have joined the same issue, so no issue is hidden, only its count. The same goes for two customers whose checkouts stall in the same hour on one instance: one `still-waiting` report, so read Polar's orders to see who is affected.
- Every limit lives in memory on each server instance, with nothing to share it, by design (no store, spec 0001). Two warm instances forward up to twice as much, and a cold start or a deploy begins at zero. Sentry's free plan has no key limit to back them up, so a server failure left running for weeks still spends the month at one report an hour for each instance, and a few of them together can use it up.
- Once an instance's 20 page reports for the day are spent, a real page failure later that day goes unreported from that instance, whether the 20 went to a forger, to extensions' rejections or to a broken script of ours. Page reports are the ones a script can forge, so they are the ones that wait. `still-waiting` alone never waits on the budget (AC-29), so a stalled paid checkout is still reported, at most once an hour. In the same way, one forged page report silences the real report of that shape on that instance for the hour (one forged `engine-unavailable` hides a real one, and one forged `still-waiting` a real one), and since 23 page report shapes draw on a budget of 20, a forger can spend a day's budget on one instance with 20 posts.
- `browser-crash` with `kind: "rejection"` includes rejections from Clerk's scripts and from extensions (AC-17), so read it as "something rejected on this kind of page", not "our code failed".
- When the proxy fails, the first failure of each hour waits for its send (up to 3 seconds) before Next.js answers with its error page. Next.js's own edge wrapper waits the same way.
- Why the proxy needs its own catch, and how many times a failed page calls the hook, are read from Next.js 16.3.5's compiled code, as `ROUTE_KINDS` is. An upgrade can change either (Follow-up). The collapse keeps a failed page to one report however many calls there are, but if the hook starts hearing the proxy, one proxy throw sends two reports until the proxy's catch comes out, because the two run in separate bundles with separate memory.
- Two small pieces of module level state, which `AGENTS.md` allows as deliberate caches: `REPORT_MEMORY` in `src/telemetry/server.ts` (the collapse and the page budget) and the page load `Set` in `src/telemetry/client.ts`.

**Neutral**:
- A new capability folder, `src/telemetry`, with its own lint zone. `AGENTS.md`'s folder list and walls need it (`/sync`).
- `/tool` posts to a second same origin path. `connect-src 'self'` already allows it, so neither policy changes.
- The scope's note that "the console ban lifts narrowly for its one reporter" no longer applies. No reporter writes a log.
- Go live step 3 asks less of Sentry than before: two alerts and the IP setting, and no key limit.
