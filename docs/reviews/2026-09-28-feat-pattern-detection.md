# Review, feat/pattern-detection, 2026-09-28

**Reviewed by**: sonnet (author on opus)
**Scope**: 68 files (plus pnpm-lock.yaml and six binary PDF fixtures), feat/pattern-detection vs main (merge base 27b25c2, 15 commits)
**Verdict**: Approve

## Summary

This lands spec 0005, pattern detection: a pure `src/detect` folder (email and phone, release 1) called from a new engine step, `src/engine/find.ts`, that walks characters, hands text blocks to the detectors, turns spans back into quads and targets, and blocks anything the engine's own target validation would refuse before a visitor can tick it. It also carries three amendments to the redaction engine that this review was asked to weigh with extra care: a code point repair in `walkCharacters`, a split of `validateTargets` into three named predicates, and `checkpoint` moving out of `redact.ts` into `failure.ts`. I traced all three against the merge base line by line and found every one behaviour preserving for the redaction path (detail below). The rest of the diff is disciplined: the lint zones for `src/detect` and the `@/detect`/`libphonenumber-js` bans are correctly threaded through every zone that needs them, the worker still never throws across the boundary and still carries no document text beyond `text`/`before`/`after`, the session reducer's new guards for a blocked match are exhaustively tested, and the UI primitives stay presentation only. `pnpm typecheck`, `pnpm lint` and `pnpm test` (1414 tests) all pass clean on the branch as it stands. I found no Blocker and no Major. Two Minor findings below are narrow, non-safety-affecting edge cases in the new find step.

## Steering question: does the self check's refusal, and its order, change?

**No. Unchanged**, on both the checks the self check performs and the order `validateTargets` reports them in.

**(a) The U+FFFF repair in `walkCharacters` (`src/engine/characters.ts:168-224`) cannot make the self check see text as gone when it is still present.** Every walked character is either visited with a code point verified consistent with the walker's own low-16-bit value (`(repaired & 0xffff) !== code` at line 197, thrown as `unsupported` otherwise), or the read throws before returning. There is no path where a character is silently dropped or skipped while the function returns normally: `onChar` always calls `visit()` after a successful repair, `endLine` cross-checks the per-line count (`onLine !== whole[line]?.length`, line 215-216), and the whole-page count is checked again after the walk (`line + 1 !== whole.length`, line 220). A throw from any of these, wherever it occurs, in `recordPage` or in `comparePage`'s use of the same reader inside `checkOutput`, is caught by `checkOutput`'s outer `try`/`catch` (`self-check.ts:56-85`, byte-identical to the merge base) and turned into `redaction-incomplete`. So the repair's only failure mode is to refuse the run, never to pass one that still holds the text. `self-check.ts` was not touched by this branch at all.

**(b) The `validateTargets` split (`src/engine/targets.ts`) is behaviour preserving.** Against the merge base (`git show 27b25c2:src/engine/targets.ts:69-116`):
- Check 1 (outline soundness plus the character-containment string test) used to run per page as two sub-steps (a pre-walk quad/text sanity throw at old lines 74-82, then a post-walk containment throw at old lines 96-102), both before the next page in the same `for` loop. The new code merges both sub-steps into one predicate, `unsoundTargetsIn` (`targets.ts:141-181`), called once per page through `unsoundTargets` (`targets.ts:128-135`) inside the same per-page loop (`targets.ts:75-82`). Both versions throw `unsupported` for the same page, before the next page's check runs; the new version reads the page's characters unconditionally rather than short-circuiting before the walk when a target's own quads are already unsound, but since a MuPDF throw during that walk is caught and remapped to `unsupported` either way (`onPage`, both versions), the observable kind is identical regardless of which sub-check fires first internally.
- Check 2 (slant) is an unchanged predicate, extracted verbatim into `slantedTargets` (`targets.ts:103-107`), still run in its own loop over every page's targets after check 1 has cleared for every page (old lines 105-109, new lines 84-88), still `slanted-text`.
- Check 3 (image reach) changes its return shape from a single page-wide boolean (`imagesWithinReach`, old `pixels.ts:30-70`, aggregated across every target's quads with an early-exit-once-false optimisation guarded by `if (!within) return;`) to one verdict per target (`imageReachVerdicts`, `pixels.ts:32-74`, monotonic OR into `overreaches[at]`, never reset). `.some(Boolean)` over the per-target array (`targets.ts:90-94`) is logically equivalent to the old single `!within`: an area belongs to exactly one target, so "some area anywhere fails" and "some target's own area fails" are the same condition. Still the last loop, still `redaction-overreach`.

  The per-target split exists so `find.ts` can ask the same predicate per match (spec 0005, INV-3) without a second implementation; `tests/unit/detection.test.ts` (`"give each target the answer it gets alone"`, around line 645) proves `imageReachVerdicts(page, targets)` on the full set equals the concatenation of asking each target alone, which is the property the redaction path relies on.
- The three loops still run in the fixed order unsound-outline &rarr; slanted &rarr; image-overreach, matching `validateTargets`'s own docstring ("`unsupported` outranks `slanted-text`, which outranks an image blanked too far"), unchanged from the merge base.

**(c) `checkpoint` (`src/engine/failure.ts:42-45`) is the same function, moved.** Its body (`await new Promise<void>((resolve) => setTimeout(resolve, 0)); if (isCancelled?.()) throw new RunCancelled();`) is character-for-character what used to be a closure inside `redactDocumentWith` (`git show 27b25c2:src/engine/redact.ts:95-98`). `redact.ts` now imports it as `checkpoint as yieldThenCheck` and wraps it back into a zero-argument closure (`redact.ts:90`) called at exactly the same six points in the pipeline. Nothing about cancel/abort semantics, what it throws, or where `redactDocumentWith` calls it has changed; the move only lets `find.ts` share the same yield-then-check for detection's own cancellation (AC-11), which is a new caller, not a changed one.

**What the self check refuses, and in what order, is unchanged before and after this branch.**

## Minor

### 🟡 A hidden replacement-text match is not deduplicated against an ordinary-mode match whose own quads are unsound, `src/engine/find.ts:134,140`

**Problem**: `covering` (line 134) is built as `targets.flatMap(({ quads }) => quads.filter(isSoundQuad))`, i.e. only the *sound* quads of every ordinary-mode candidate on the page. A `hidden` (replacement-text-ignored) candidate is deduplicated against `covering` by point containment (line 138-141). If an ordinary-mode match's own quads are unsound (so that match is separately blocked `unsound-outline`), none of its quads pass `isSoundQuad`, so it contributes nothing to `covering`. A `hidden` candidate whose characters sit at that same location would then not be recognised as already covered, and would be listed as its own extra row, blocked `replacement-text`.

**Why it matters**: this is a narrow deviation from the feature design's stated invariant, "one place on the page is one row" (spec 0005, *Feature design*, *Relationships*). It requires a target with genuinely degenerate quad geometry (self-intersecting, zero-area, or otherwise failing `isSoundQuad`) that also happens to sit over replacement text, an unusual combination. It has no safety consequence either way: both rows would already be disabled and untickable (one for `unsound-outline`, the duplicate for `replacement-text`), so no over or under removal follows. It is a checklist UX quirk, not a correctness or privacy issue, and I did not find a fixture or test exercising it.

**Suggested fix**: either use each target's full `quads` (not filtered to sound ones) when building `covering`, matching how `unsoundTargetsIn` already treats an unsound target as fully blocked regardless of geometry, or add a one-line comment noting the interaction is intentionally left alone because the duplicate row would be equally untickable. Not blocking.

### 🟡 `windowsFrom`'s early return on `opening.date` skips only the window's first unit, not the whole run, `src/detect/phone.ts:483-485`

**Problem**: `windowsFrom(run, first, ...)` returns `[]` immediately when `run[first].date` is true (a unit that is itself a full numeric date). This correctly stops a window from *starting* on a date unit, but `chosenIn` still calls `windowsAt(first)` for every `first` in the run, including indices whose unit is a date, and each such call does the (cheap) date check again and returns empty. This is not a correctness bug (INV-14 holds: no window ever starts or grows through a date unit, since the in-window loop also breaks on `unit.date` at line 494), just a slightly redundant existence check duplicated across two code paths (the guard at 484 and the growth-loop guard at 494) with no comment tying them together.

**Why it matters**: purely a maintainability nit bordering on a Minor, since a future edit to one guard without the other could silently reopen INV-14 (dates read as phone numbers). No test failure results today; `tests/unit/detect-adversarial.test.ts` and the "look alikes" cases in `tests/unit/detect-phone.test.ts` do cover dates thoroughly, so a regression here would likely be caught. Flagging only so the two guards are recognised as one invariant rather than two independent ones.

**Suggested fix**: a short comment at one of the two guards pointing at the other ("also guarded at line 494 for units after the first") would make the duplication legible. Not blocking.

## Nits

- ⚪ `src/engine/targets.ts:128-135`, `unsoundTargets` reads the page in `EXTRACTION_OPTIONS[0]` itself while `unsoundTargetsIn` takes characters already read; both are exported, and it is easy to call the wrong one from a new call site without noticing the double read. The docstring already explains the split, so this is only a naming suggestion (e.g. `unsoundTargetsOnPage` vs `unsoundTargetsIn`) for a future reader skimming imports.
- ⚪ `src/detect/phone.ts:169-197`, `MAX_WINDOW_DIGITS` and `MAX_PARSES_PER_GROUP` are derived at module load with `Math.max(...PHONE_READINGS.flatMap(...))`; correct and well commented, but worth a passing note that a future edit to `PHONE_READINGS` that removes every row (emptying the spread) would make `Math.max()` return `-Infinity` silently rather than fail loudly. Extremely unlikely to matter in practice given the table is a fixed constant.

## Strengths

- The three engine amendments this review was asked to weigh most carefully (the U+FFFF repair, the `validateTargets` split, and `checkpoint`'s move) are all behaviour preserving and, in the repair's case, fail closed by construction rather than by convention: every path either returns a verified character or throws, with the fail-closed cases (`tests/unit/characters.test.ts`, `"a repair that cannot line up"`) exhaustively pinned, including JSON that fails to parse, a line the walker never reached, and mismatched counts in both directions.
- `src/detect` is genuinely pure and linear: no detector regex has a nested quantifier, email is found by bounded outward scans from each `@` rather than one backtracking pattern, and the phone finder's window growth is capped at `MAX_WINDOW_DIGITS` with a block-wide memoised judge, backed by `tests/unit/detect-adversarial.test.ts`'s parse-count assertion against `MAX_PARSES_PER_GROUP` through a `vi.mock` wrapper around the real parser.
- INV-2/INV-3 (a match may be ticked exactly when the engine would accept it) is enforced by construction rather than by two independent implementations agreeing by luck: `find.ts` asks the exact same predicates (`unsoundTargetsIn`, `slantedTargets`, `imageReachVerdicts`) that `validateTargets` calls for the redaction path, in the same AC-8 order, so a match detection leaves unblocked cannot later be refused for a reason detection didn't already check.
- The lint zones for `src/detect` correctly restate every restriction the wall needs (mupdf, `@/engine`, `@/ui`, `@/lib`, `@/config`, react/next, every `@/worker` import except `import type` from `@/worker/protocol`), and the "no `search()`" ban is threaded through both `redactnest/engine-wall-engine` and `redactnest/detect`, matching the ESLint flat-config "later block replaces" trip wire called out in root `AGENTS.md`.
- Session/worker wiring for a blocked match is exhaustive: `tick-toggled` refuses a blocked match (`src/lib/session.ts:213-217`), `seededTicks` excludes it (`session.ts:128-134`), and the worker gives it no target at all (`engine.worker.ts:196-197`), so a hand-crafted `redact` naming a blocked id fails as `unsupported` through the pre-existing "unknown target" check with no new code path, exactly as the spec's Decision section calls for.
- `pnpm typecheck`, `pnpm lint` and `pnpm test` all pass with no findings surfaced by any of the three (1414 tests, 37 files).

## Test coverage

Thorough and squarely aimed at the areas that matter. `tests/unit/characters.test.ts` pins the repair's fail-closed behaviour in both directions (JSON richer than the walk, JSON poorer than the walk, a mismatched low-16-bit value, unparseable/malformed JSON) and proves the structured text is always destroyed. `tests/unit/detection.test.ts` proves the split predicates give identical per-target answers whether asked together or alone (the property the redaction path depends on), and separately proves every unblocked match in the fixture set redacts alone and together. `tests/unit/detect-phone.test.ts` and `detect-adversarial.test.ts` cover the rebuilt finder's side-by-side numbers, look-alikes, every grouping, the two libphonenumber-js pins, and the parse-count bound. `tests/unit/detect-email.test.ts` covers the rejoin's narrower-than-a-plain-join rule. Component and e2e coverage (`tests/component/review-checklist.test.tsx`, `tests/e2e/review.spec.ts`, the extended `privacy.spec.ts` and `design-system.spec.ts`) close the loop through the UI. The two Minor findings above are narrow edge cases in interaction between independently well-tested pieces (`find.ts`'s dedup filter, and the two INV-14 guards in `phone.ts`); I would not block on either, and neither is the kind of gap `/check verify`'s browser pass would be expected to catch on its own.
