# Review, feat/redaction-engine, 2026-09-27

**Reviewed by**: sonnet (author on opus)
**Scope**: 89 files, feat/redaction-engine vs main (merge base d35f337, 16 commits plus uncommitted work and one untracked test file)
**Verdict**: Approve with nits

## Summary

This lands the redaction engine (spec 0004, slices 1 to 5). It does real removal of text, pixels and line art through MuPDF, rebuilds the file from an allowlist so everything else is stripped, and runs a self check in three parts (structure, characters in two extraction modes, pixels) that refuses to hand back any file it cannot prove clean. The code follows an unusually detailed and rigorous spec very closely. The geometry, the redaction pass settings, the character comparison, the slant and image reach refusals, and the slice 5 fix (extraction without clipping) are all there as specified, with named constants and comments that cite the invariant they uphold. The engine wall holds, document bytes are transferred rather than copied, and error payloads carry a kind only. Test coverage is exceptional. The fixture matrix, the tests that prove each self check fires, and the `bounds-pin.pdf` and `next-line-*.pdf` pins aim squarely at the "looks redacted but is not" failure this review was asked to weight heaviest, and I could not find a gap in them. The one real finding is a narrow ordering gap in how the worker evicts a session when a new open reuses the same `jobId`. It is likely unreachable today, and no test covers it either way.

## Minor

### 🟡 An open that reuses the same `jobId` does not wait for that job's run to settle before parsing the new document, `src/worker/engine.worker.ts:153-190`

**Problem**: In `handleOpen`, the first eviction pass (`const evicted = [...sessions.entries()].filter(([existing]) => existing !== jobId)`, lines 153 to 158) and the wait at line 165 (`await Promise.all(evicted.map((session) => session.runs))`) both leave out any existing session whose key equals the incoming `jobId`. So if an `open` arrives with the *same* `jobId` as a session whose run is still in flight, that session is not in `evicted`. `openDocument(bytes, limits, ...)` at line 168 then goes ahead at once, without waiting for the old run to notice it was cancelled, destroy its working copy, and let go of `session.bytes`. The old session is cleaned up only afterwards, by the second eviction loop at line 182 (`for (const existing of sessions.keys()) endSession(existing)`), which runs after the new document is already open.

This is the one path through `handleOpen` that does not keep the ordering `AC-23` promises for every other replacement: "the new document is not parsed until the run has destroyed its working copy and let go of the old bytes." When a different `jobId` replaces an old one, the wait is proven by `tests/unit/engine-worker.test.ts` ("cancels the run in flight when a new document arrives, and waits for it"). This case is not proven, because the `!== jobId` filter treats the job's own earlier session as if it were not a session to wait for.

**Why it matters**: I could not find a call site in this diff that sends the same `jobId` again while that job's own redaction run is active. `handleRetry` and the `onEngineLost` automatic retry both reuse `jobId`, but they reach `runOpen` only for a session that is `lost`, or when `loadNeverFinished` is true. That is before a redaction could have started. Both also call `releaseEngine()` first, which (in the unchanged `src/worker/client.ts`) most likely tears down the `Worker` and starts a fresh one, so the old `sessions` map at module level would hold no entry to race against. So this is plausibly unreachable with today's two callers. But nothing in `engine.worker.ts` states or checks that constraint. There is a comment for why the immediate `endSession` skips `jobId` (you should never end the session you are about to open), but none for why the AC-23 wait may skip it too, which is a different concern. And no test shows what happens if an open with the same `jobId` arrives during a run. If a later change ever does that (a new retry path, or a bug in `client.ts`), the new document could be parsed while the old run still touches the old `bytes`, and the two `openDocument` and `redactDocument` calls would race without the ordering AC-23 promises everywhere else.

**Suggested fix**: You could either (a) add a short comment at the `evicted` filter explaining why an open with the same `jobId` can never have an active run to wait for, tying it to the two call sites and to how `client.ts` replaces the worker, so the invariant is stated rather than assumed, or (b) make the wait unconditional, collecting the `runs` of *every* current session (without filtering out `jobId`) before opening. Waiting on a queue that has already settled costs nothing when no run is in flight. Either way, a test that opens, starts a redaction, then sends a second `open` with the *same* `jobId` and checks the ordering would close the coverage gap.

## Strengths

- The self check is real defence in depth against exactly the failure this review was asked to weight heaviest. Two extraction modes (ordinary and `ignore-actualtext`) catch a surviving glyph as well as surviving replacement text. Extraction without clipping (`CHECK_EXTRACTION_OPTIONS`) catches MuPDF's content filter fault with `'` and `"`, which moves ticked text off the page instead of removing it (`next-line-0.pdf` to `next-line-4.pdf`, in `tests/unit/redaction-matrix.test.ts`). The pixel check decodes images again on its own rather than trusting the padded pass. The structural check walks every object rather than trusting the allowlist alone. `tests/unit/redaction-check.test.ts` proves each part fires by switching it off through the `Pipeline` test seam, which is the right way to show a safety net actually holds something.
- MuPDF's own quirks are pinned, not assumed. `bounds-pin.pdf` and the "MuPDF acts on each area's bounds" suite in `redaction-matrix.test.ts` drive MuPDF directly to prove the exact behaviour `BOUNDS_REACH_RATIO` is built on. A MuPDF upgrade that changed that behaviour would fail a test rather than quietly widen what a pass can reach.
- The engine wall holds. Only `src/engine/*.ts` imports `mupdf`, and only `src/worker/engine.worker.ts` imports `@/engine` (checked by searching all of `src/`). Document bytes are transferred rather than copied at every hand off I traced. The one deliberate copy (`takeOutput` in `redact.ts`) copies MuPDF's own heap buffer just before it is freed, and the comment says why it matters.
- Error payloads and logs carry a kind only, and that is proven. `EngineFailure` and `RunCancelled` carry nothing but a kind and a fixed message. `tests/unit/engine-worker.test.ts` checks that a secret string never reaches a posted message, even when the underlying error's own message contains it. The type level gate in `LoggablePayload` is unchanged and still passes.
- The geometry and the self check's tolerance and grid code (`characters.ts`, `geometry.ts`) hold up. The grid cell is sized to `POSITION_TOLERANCE` and probes its 3 by 3 neighbours, so a match within tolerance can never fall outside the searched area. `isSoundQuad`, `containsPoint` and `boundsReach` are careful and fail closed (a `NaN` carries through to a refusal), and the geometry unit tests exercise them at the boundary values the spec names (for example `isTooSlanted` "just past" the ratio).

## Test coverage

Very thorough, and aimed squarely at the risk this feature exists to manage. `tests/unit/redaction.test.ts`, `redaction-matrix.test.ts`, `redaction-check.test.ts`, `redaction-geometry.test.ts` and the new `redaction-inventory.test.ts` drive real MuPDF in Node over fixtures written by hand (never written by the engine). They check removal at three independent layers per case: structured text extraction, a search of the decompressed bytes in both PDF string encodings, and (for images) direct pixel decoding. None of them trusts the engine's own account of what it did. The worker's queueing, cancellation and replacement logic is exercised with a gated fake engine covering every AC-17, AC-18 and AC-23 interleaving I could think to check, except the one narrow gap above. `tests/component/tool-client.test.tsx` and the `tests/e2e/*.spec.ts` suite close the loop through the UI and a real browser (cancel, download, privacy, console silence). I found no untested new branch of consequence in the production files reviewed.

## Open follow-ups

### Owed to feature 8 (Redact flow): `retireOtherJobs` still skips the same `jobId`, `src/worker/client.ts:201`

**Status**: open. Found while fixing the minor finding above in `eda4c3a`, and left alone there because it lives on the main thread, outside that fix.

**Problem**: `retireOtherJobs` cancels and settles every pending operation except those under the `jobId` being opened (`if (operation.jobId === jobId) continue;`). The worker makes no such exception. `handleOpen` always ended a same `jobId` session in its second eviction pass, and since `eda4c3a` it does so before parsing, cancelling that session's run in flight. A cancelled run posts nothing. So if an `open` with the same `jobId` ever reached a live worker while that job's redaction was pending, the worker would stop the run and the main thread's promise for it would never settle. The visitor would be left on a run that neither finishes nor fails.

**Why it is not live today**: both callers that reuse a `jobId` reach a fresh worker. The `onEngineLost` automatic retry calls `releaseEngine()` first. `handleRetry` runs only from `lost`, and `worker-lost` is dispatched only inside the `onEngineLost` callback, after that same `releaseEngine()`. `releaseEngine()` settles every pending operation (`failAll`) and terminates the worker, so nothing is left to race.

**Why feature 8 owns it**: feature 8 builds the full redact flow (tick, redact, download, run again). That is where a new path that reopens a job on a live worker would most likely appear, so it should check this constraint when it adds one.

**Suggested fix**: you could drop the `jobId` exception in `retireOtherJobs`, so every pending operation is settled as cancelled, the same rule the worker now follows. The new open is added to `pending` only after `retireOtherJobs` runs, so it would not retire itself. Then add a test in `tests/unit/worker-client.test.ts` that sends a same `jobId` open while a redact is pending and checks that the redact settles as cancelled.
