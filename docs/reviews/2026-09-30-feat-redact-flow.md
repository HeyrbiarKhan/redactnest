## The engineer's steering

### A. GA care on shared code

**`contextReader` (`src/engine/find.ts:470-492`): correct, with one gap in the tests.**
- The two comparisons are exact and match AC-9. `beforeCut` is `at[start] - reach > 0`, which is precisely "the slice started after position 0", and `afterCut` is `at[end] + reach < collapsed.length`, precisely "the slice ended before the end". A match with exactly `reach` code points before it is not cut, and one with `reach + 1` is. I checked the boundary cases in a scratch copy of the function: exactly at the reach on both sides, reach 0 (both flags true, both strings empty, so the row shows nothing), a collapsed run of whitespace before and after the match, and a page that ends in whitespace (the trailing collapsed space counts as text, so a match near the end of a page that ends in a newline shows no "…" after it).
- Cuts are counted in the same unit as the slice, code points of the collapsed text, so a surrogate pair is never split by the flag and the flag never disagrees with the string. A base letter and its combining mark can still be split by the reach, exactly as before this branch; that is unchanged and cosmetic.
- The privacy ceiling is untouched. `reach` is still `Math.max(0, Math.floor(contextChars))` and `before` and `after` are cut exactly as before, so each side stays at or under `config.matchContextChars` (ceiling 200, spec 0002 INV-9). The only addition is two booleans per match, which says "the page goes on" and reveals nothing the context did not.
- Every caller still gets what it got. `context(target)` and `hiddenContext(target)` are spread into `FoundMatch`, which now requires the two fields, so a caller that missed them would fail `pnpm typecheck`; the worker maps them into `ReviewMatch` and `engine-worker.test.ts` pins the exact key set.
- Gap: see Minor 1. The tests pin the direction of the flags but not the exact boundary that the two comparison operators decide.

**`retireOtherJobs` (`src/worker/client.ts:189-215`): this branch fixed the hazard, and added no path that reaches it.**
- It dropped the `jobId` exception, so a same `jobId` open settles every pending operation as cancelled and posts a cancel for each. The new open is added to `pending` only after the call, so it never retires itself, and the worker keys a cancel on the operation id, so the new open is untouched. `handleOpen` ends a same `jobId` session in the worker and cancels its run, so the main thread and the worker now agree.
- Callers: `openSession` has one call site, `runOpen` in `tool-client.tsx`. Its three entries are a new file (a fresh `jobId`, so behaviour is exactly what it was), `handleRetry` and the silent retry in `onEngineLost` (same `jobId`, but `releaseEngine()` ran first, so a new worker and an empty `pending`; the dropped exception is a no-op for both). The new `rerun` edge sends `redact`, never `open`. So today the change is pure hardening, as AC-24 says.
- Tests: `tests/unit/worker-client.test.ts:781` settles a pending redact as cancelled on a same `jobId` open, asserts the cancel message went out for the redact id and not for the new open, and that the new open still resolves; the worker half (a same `jobId` open waits for the run in flight) was already pinned at `tests/unit/engine-worker.test.ts:1133`. One harmless residue: a cancel that reaches the worker after the operation has already finished leaves that id in the worker's `cancelled` set for good (a UUID, never reused). That was true for other jobs before this branch.

### B. Notes from `/check verify`

**Focus passing through `body` (no fix required; one optional word).** The settled focus is right in every row of the *Focus* table, and the component suite asserts it (`tests/component/tool-client.test.tsx:2563`) as does `flow.spec.ts`. The transient is real but only for the changes that arrive from a promise: a click driven change (Redact to Cancel, Download to Redact another PDF, a tick) is a discrete event, so React flushes its passive effect before paint, but Cancel to Redact, a run completing or being refused, and an open failing dispatch from a promise callback at default priority, so the effect runs after a paint with focus on `body`. That is not a WCAG 2.2 AA failure (2.4.3 is about the order focus takes, and browsers keep the sequential focus starting point at the removed control, so a Tab in that gap does not lose the place; a screen reader pass was fine), but AC-20's literal wording is "never on `body`". The smallest fix is `useLayoutEffect` instead of `useEffect` on the focus effect at `tool-client.tsx:280`: refs are attached before layout effects run, it runs before paint whatever the event priority, and React 19.2 has no server warning for it. See Nit 1.

**`unsupported` and `edge-text` unreachable as run refusals (small gap, narrower than it sounds).** Both are reachable from committed fixtures, but at open: `trim-refused.pdf` opens as `edge-text` and `trim-quote.pdf` as `unsupported` (`tests/unit/trim.test.ts:522-538` asserts both, and the same file through `redactDocumentWith`). The engine path is therefore covered, and the worker's run time `unsupported` from `trimAgrees` is covered by a mock (`engine-worker.test.ts:805`). What no test proves in a real browser is the page copy for those two kinds, and the run variant (the refusal callout with "Choose another PDF") cannot occur from any fixture by design, because a run's trim reads the same bytes the open's did, so a document that opens cannot then fail its trim. That leaves the component test (`tool-client.test.tsx:2296`) as the proof for the run variant, which is adequate. The cheap addition is the two open failures in `flow.spec.ts`; see Minor 4. Reading the copy that way also turned up Minor 2.

**`detect-blocked.pdf` refused on default ticks (a real UX limit, and spec 0007 records it rather than solving it).** That fixture pins spec 0005's honest limit: an address inside wider replacement text with equal glyphs is listed tickable and ticked by default (a detector cannot know), and the run then fails with `replacement-text`. A real document of the same shape sends a visitor to a refusal on their first, default run, and the guidance is "Untick one group at a time to find it". With two groups that finds a kind, not an item, so on a 1,100 row list the only way out is to untick every address of the kind and ship a file that still holds them (the result card does say so under Left in the file, so it fails honest and closed, not unsafe). Spec 0007 acknowledges it under Consequences ("the visitor unticks by guesswork") and Follow-up 1 (name the refused item), and defers the fix to feature 11's refusal counts, because naming a target changes the error shape (spec 0002 INV-4). That is a defensible deferral, not a defect in this branch, but see Minor 5 for making it harder to lose.

## Major

### 🟠 The AC-8 first render budget is a wall clock assertion that fails under the suite's own parallelism, `tests/e2e/checklist-speed.spec.ts:136`

**Problem**: The test measures from the worker's `result` reply to the first paint after the checklist is in, and fails at 1,000 ms. In a project with `fullyParallel: true` (`playwright.config.ts:32`), every other spec is opening documents in the same moment, and the paint is what starves. On this machine: alone with `--workers=1`, `firstRenderMs` 140 (commit 111); beside `flow.spec.ts`, 2,415 (commit 305, so 2.1 s of it was waiting to paint), then 451 and 602 on two repeats; and in the full `pnpm exec playwright test`, 7,641 (commit 407) and the run finished 204 passed, 1 failed, this being the one. The tick budget (200 ms) held everywhere (11 to 52 ms). `AGENTS.md` already records this hazard for the same suite ("workers opening documents side by side ... starved the 10 MB engine download").

**Why it matters**: `pnpm test:e2e` is red on a healthy tree, on the very spec AC-8 says must keep asserting both lines "on every browser run". CI has `retries: 2`, which will turn most of these into passes, and then a real regression back to per row rendering has to fail three times in a row to be seen. A gate that cries wolf is ignored, and this one guards the freeze the feature was built to remove.

**Suggested fix**: Take the measure out of the parallel pool: its own Playwright project with one worker that runs after the others (`dependencies` on the main project, or `testMatch` split and run as a second step), so it times the page and not the machine. And stop asserting paint time against a fixed line where contention can move it; the tick line and the deterministic render count in `tests/component/checklist-renders.test.tsx` already pin the mechanism, so the first render line could be checked on the React commit (`toCommitMs`, 111 to 508 here) or given a margin that only the old per row behaviour (seconds, not tens of milliseconds) could cross. Record in `rationale.md` that the figures were taken with one worker.

## Minor

### 🟡 The tests pin the direction of `beforeCut` and `afterCut`, not the boundary, `tests/unit/detection.test.ts:232` and `src/engine/find.ts:489`

**Problem**: AC-9 is defined by two exact comparisons, and the three tests use reaches far from the edge (20 and 3 on `detect-email.pdf` and `detect-blocked.pdf`, 200 with an implication that only runs one way: "if the context is shorter than the reach, it is not cut"). Nothing tests a side that holds exactly `reach` code points (not cut) against one that holds `reach + 1` (cut), which is the only place `> 0` versus `>= 0` and `<` versus `<=` differ. The collapsed whitespace mapping (`at[]` skipping a repeated space) is untested with a flag.
**Why it matters**: A one character slip in either operator would show a wrong "…" on exactly the matches that sit at the reach, and nothing would fail.
**Suggested fix**: In `detection.test.ts`, use `detect-email.pdf`'s first match, whose `before` is "Contact: " (9 code points): at `contextChars` 9 assert `beforeCut` false, at 8 assert true with `before` "ontact: "; do the same for `afterCut` at the page's last match, and add one case where a run of spaces sits inside the window.

### 🟡 The copy for `unsupported` and `edge-text` tells an open failure to change what is ticked, `src/lib/flow-text.ts:76` and `:117`

**Problem**: The two kinds share one entry between open failures and run refusals, and both end "Changing what's ticked won't help with this file." When the open fails there is no checklist, so the visitor has ticked nothing. It also gives them nothing to do: the next step is a statement about ticks and no route on (save or print a fresh copy, try another file).
**Why it matters**: `trim-refused.pdf` and `trim-quote.pdf` are exactly these open failures, and `AC-15` shows the copy above the full drop zone, so a first time visitor reads advice about a screen they have not seen.
**Suggested fix**: Either give the two kinds separate open and run wording (the copy record is a function of the entitlement already, so it can take the context), or phrase the next step so it reads correctly in both places ("Choosing different items won't help; try a different copy of the file"). Spec 0007 lets `/develop` polish the words, so this needs no spec change.

### 🟡 Start over discards a run in flight or an undownloaded result without the confirm that Choose another PDF gets, `src/app/tool/tool-client.tsx:404`

**Problem**: `handleFile` asks first when `hasUnsavedWork` is true; `handleStartOver` releases the worker and the session with no such check. This is not new, but this branch puts Start over in the file bar beside Choose another PDF in every step (AC-3: "both buttons stay enabled in every state, a run included"), so a finished, undownloaded result or a long run now sits one slip away from a link that throws it away silently while its neighbour asks.
**Why it matters**: The two controls look like siblings and behave differently about the same loss; the tool's own non negotiable is not to lose work quietly.
**Suggested fix**: Decide it deliberately: either ask through the same `REPLACE_WARNING` path when `hasUnsavedWork` is true (Redact another PDF, which only appears after a download, never triggers it), or record in spec 0007 that Start over is meant to be unguarded.

### 🟡 The open failure table in the browser suite leaves out the kinds fixtures can reach, `tests/e2e/flow.spec.ts:281`

**Problem**: `OPEN_FAILURES` covers a damaged file, a non PDF, the page cap and layers. `trim-refused.pdf` (`edge-text`) and `trim-quote.pdf` (`unsupported`) are committed and open failures in a real engine, and are the two kinds the verify note called unreachable. Nothing browser side shows their copy, focus on the heading or the full drop zone beneath.
**Why it matters**: They are the two kinds whose copy has the tick wording in Minor 2, and the only ones a real fixture can put the visitor in front of.
**Suggested fix**: Add both rows to the table (title and a phrase from the body), then leave the run variant to the component test as it is.

### 🟡 A refusal on default ticks has no way to find the item, and nothing keeps that follow up alive, `docs/specs/0007-redact-flow/index.md:318` and `src/lib/flow-text.ts:129`

**Problem**: See answer B above. `replacement-text` copy sends the visitor to "untick one group at a time", which cannot isolate a row in a list of hundreds, and the trigger for revisiting it is feature 11's refusal counts, which are not built.
**Why it matters**: For that document shape the default path is a guaranteed refusal and the recovery is to give up removing a whole kind.
**Suggested fix**: Keep Follow-up 1 and give it a trigger that does not wait on telemetry: for example, bring back to `/architect` a worker side bisect on refusal (re run per target set, return the ids as blocked, so the review comes back with the offender blocked rather than named), which needs the error shape decision but no new data crossing the boundary beyond match ids the main thread already holds.

## Strengths

- The session machine is exactly as small as it needs to be: `ticks-set` returns the same object when nothing changes, `rerun` is only reachable from a downloaded `complete`, a refusal edge keeps the review, and late `redacted`, `failed` and `cancelled` replies are ignored outside `redacting`. `tests/unit/session.test.ts` walks every new edge and the unchanged ones.
- A failed run cannot produce output and a cleaned copy cannot pass for a redaction: `outputFormFor` names the file from what the engine removed, then from the readings, and the result title, the file name and the `PARTLY_REASON` line all follow it (`flow.spec.ts` proves it on `read-mixed.pdf` end to end).
- Failure copy is a record over `EngineErrorKind` with a scan for forbidden promises, the free and paid `too-many-pages` forms, a "never 0 MB" size floor, and the lost worker's words kept apart from the engine load failure's.
- The checklist render count test drives the real reducer with counting wrappers on the two row primitives and asserts one row, one select all and one commit per tick, which is the mechanism behind AC-8 rather than a stopwatch. `content-visibility` is applied with the padding that keeps the focus ring inside the paint clip.
- The `retireOtherJobs` change follows the earlier review's fix and test to the letter, and the comment says why the new open cannot retire itself.
- New boundary data is two booleans, pinned in the worker's exact key list test, and `ResultCounts` joins `LoggablePayload` under the type level gate.
